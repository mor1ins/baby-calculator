# Frontend

Реализован мобильный React/Vite-клиент: вход/регистрация, день, графики, история, профиль и административный просмотр. Формы — React Hook Form; API через инжектируемые HTTP-репозитории и шину, серверное состояние — TanStack Query. Правила разработки и тестов — в [AGENTS.md](AGENTS.md).

## Команды

Node.js 24 используется в CI; зависимости фиксируются в `package-lock.json`.

```sh
cd frontend
npm ci
npm run check
npm run dev
```

Приложение доступно на `http://localhost:5173`. У backend задать `BABY_PUBLIC_ORIGIN=http://localhost:5173`. Vite проксирует `/api` на backend `http://127.0.0.1:8000`; production должен обслуживать SPA и `/api` на одном origin, с fallback маршрутов на `index.html`. Сборка — `npm run build`, результат в `dist`; локальный просмотр — `npm run preview`. Секреты во frontend не передаются.

Маршруты: `/`, `/schedules`, `/history`, `/profile`, `/login`, `/register`, `/admin`, `/admin/:owner` и страница неизвестного адреса. Backend реализует все 23 операции принятого контракта. Для полного запуска см. корневой README. API-клиент использует cookie и CSRF из сессии в памяти, передает `If-Match`, сохраняет коды ошибок и поля валидации. Автоматические повторы отключены. Отмена передается до транспорта, поздние ответы отмененного запроса не применяются.

| Команда                     | Назначение                                                                 |
| --------------------------- | -------------------------------------------------------------------------- |
| `npm run lint`              | ESLint: JS/JSX, Hooks, доступность, сортировка импортов, сложность функций |
| `npm run lint:styles`       | Stylelint: CSS; до появления CSS отсутствие файлов разрешено               |
| `npm run format`            | Форматирование Prettier                                                    |
| `npm run format:check`      | Проверка форматирования без изменения файлов                               |
| `npm run lint:architecture` | Границы слоев, циклы и неразрешимые импорты                                |
| `npm run lint:duplicates`   | Поиск повторяющихся блоков в src и tests                                   |
| `npm test`                  | Тесты правил качества (Node) и приложения (Vitest/Testing Library)         |
| `npm run check`             | Все проверки без автоисправлений и production-сборка                       |

Для исправления порядка импортов: `npm run lint -- --fix`, затем `npm run format`. GitHub Actions выполняет `npm ci` и `npm run check`. Старая версия в `only_web_version` не входит в проверки нового frontend.

## Архитектура

| Каталог              | Ответственность                                             |
| -------------------- | ----------------------------------------------------------- |
| `src/presentation`   | Компоненты React, формы, UI-состояние                       |
| `src/application`    | Сценарии пользователя и их обработчики                      |
| `src/domain`         | Чистые преобразования и клиентские правила                  |
| `src/infrastructure` | Репозитории HTTP API/локального хранения и внешние адаптеры |
| `src/contracts`      | Сообщения, DTO, интерфейсы шины и репозиториев              |
| `src/messaging`      | Шина и ограничения переходов                                |
| `src/composition`    | Контейнер и сборка зависимостей                             |

Репозиторий инжектируется в infrastructure-обработчик; остальные слои обращаются к данным через шину. Внутренний вызов репозитория не добавляет межслойный переход. Контейнер `createRuntime` использует явную инъекцию через конструкторы и параметры без отдельной DI-библиотеки. Шина считает максимум 3 обработчика на корневую команду и запрещает обратные вызовы; вложенные параллельные обращения делят один бюджет, независимые команды имеют отдельные счетчики. Чтение сессии проходит presentation → application → infrastructure. Тесты проверяют контракты репозиториев, отмену, параллельные бюджеты, восстановление после ошибок и изоляцию контейнеров. Клиентская шина и серверная шина имеют отдельные бюджеты; HTTP-запрос связывает их через API.

Dependency-cruiser анализирует граф импортов: каждый рабочий слой может импортировать только себя и contracts; contracts не импортирует реализации; composition может собирать все слои. Запрещены циклы, доступ к тестовым модулям из src, внешние runtime-пакеты в чистых слоях. Так блокируются и относительные импорты, и обходы через реэкспорты. ESLint дополнительно запрещает прямой браузерный I/O вне инфраструктуры и динамические импорты в src.

Проверки тестируются на временных файлах с заведомыми нарушениями и на допустимых примерах. Дублирование обнаруживается начиная с 5 строк и 50 токенов, допустимый процент — 0. Это не доказательство отсутствия любого повторения или смысловой связности. Статический анализ не отслеживает произвольную передачу объектов/алиасы браузерных API и фактические вызовы шины; поэтому обязательны ревью и runtime-тесты.

Конфигурации основаны на [ESLint flat config](https://eslint.org/docs/latest/use/configure/configuration-files) и [правилах dependency-cruiser](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md). ESLint 9 выбран для совместимости с peerDependencies eslint-plugin-react; обновление major требует совместимого React-плагина.

## Известные ограничения зависимостей

На 3 октября 2026 года `npm audit` сообщает 7 high-предупреждений в цепочке dev-зависимостей Stylelint, связанных с `braces` и обработкой глубоко вложенных glob-шаблонов (GHSA-vfj7-8cjw-p6xm). Обновление до Stylelint 17.16.0 их не устраняет; предлагаемый audit откат к Stylelint 7.7.0 не применяется. В проверках используются фиксированные шаблоны из репозитория. Это ограничение инструментов разработки, а не runtime приложения, и оно не считается устраненным. Проверять обновления цепочки зависимостей перед выпуском; `npm run check` проверяет качество кода и не заменяет `npm audit`.

ESLint 9 помечен npm как неподдерживаемый, но актуальный `eslint-plugin-react` пока объявляет совместимость только до ESLint 9. Обновление ESLint и React-плагина следует выполнять совместно; peerDependencies принудительно не обходятся.

Ввод времени преобразуется в часовом поясе дневника через Temporal; неоднозначное/несуществующее локальное время отклоняется. Расчеты прогноза и метрик принадлежат backend. Главный экран перечитывает данные раз в минуту и при возвращении фокуса.

## Сверка с дизайном

Источник визуальных решений — `design/SPEC.md` и `design/previews`. В интерфейсе сохранены бумажный фон, заголовки Georgia, тёмная карточка текущего промежутка, жёлтое основное действие, три плитки метрик и вертикальная линия факта/прогноза. Редакторы открываются в нативных модальных панелях; на смартфоне панель примыкает к нижнему краю. История показывает календарь, графики — цветовую схему интервалов, профиль — отдельные строки настроек.

`tests/e2e/design.spec.js` использует примеры принятого API для воспроизводимой визуальной сверки: снимает основные экраны, проверяет ширины 320/360/390/430 px, удержание фокуса и закрытие панели по Escape. Снимки пишутся в `tests/test-results/design-*.png`; это проверка структуры и поведения, а не автоматическое доказательство пиксельного совпадения. Сценарии дневника и администрирования дополнительно проверяются с настоящим backend.

## Темы оформления

В «Профиле» доступен выбор «Авто / Светлая / Тёмная». По умолчанию используется системная тема.
Выбор хранится в браузере под ключом `tishe.theme` и синхронизируется между вкладками;
при недоступном хранилище переключатель работает в текущей сессии.

Палитры находятся в `src/presentation/theme/light.css` и `dark.css`, общие параметры размеров
и типографики — в `base.css`. Обе палитры реализуют одинаковый набор семантических переменных.
`styles.css` связывает компоненты с этими параметрами. Для нового визуального состояния добавляйте
параметры в обе палитры; цвета нельзя прописывать в стилях компонентов.
В JSX и JavaScript запрещены встроенные стили и SVG-атрибуты оформления; ESLint и архитектурные
тесты проверяют этот контракт. SVG-пути графиков содержат только геометрию данных,
оформление задаётся CSS.

Настройка проходит через шину и репозиторий `BrowserThemeRepository`; композиция применяет
`data-theme` к корневому элементу до монтирования React. Входной модуль блокирует первую отрисовку;
плагин Vite сохраняет этот атрибут в сборке. Проверка браузерных сценариев (с тестовыми API-ответами):

```sh
cd tests
BABY_E2E_URL=http://127.0.0.1:5173 npm test -- theme.spec.js
```

## Общий дизайн с демо

Основное приложение использует Konsta UI 5.5, локальный Manrope и эталонные стили
`design/styles.css`, `design/refinement.css`, `design/components.css`. Последний файл
общий для демо и приложения; в `src/presentation/product.css` находятся только
адаптации рабочих сценариев. Тема сохраняется локально, iOS/Material выбираются
по платформе браузера.

`npm run dev` и `npm run build` предварительно создают `public/app.css` через Tailwind CLI.
После изменения CSS во время разработки выполните `npm run styles`.
Сгенерированный CSS не коммитится. Проверка соответствия макету:
`cd ../tests && BABY_E2E_URL=http://localhost:8080 npm test -- parity.spec.js`.
