# Правила frontend

Обязательны для кода и тестов в этом каталоге. Используем JavaScript/React; переход на TypeScript требует отдельного решения.

- Форматирование: Prettier, 4 пробела, целевая ширина 120 символов, camelCase для функций и переменных, PascalCase для компонентов и классов. ESLint проверяет JavaScript/JSX, сортировку импортов, React Hooks и доступность JSX; Stylelint — CSS. Предупреждения ESLint считаются ошибками.
- Не копировать бизнес-логику, компоненты и блоки тестов. Выносить повторяемое поведение в функции/компоненты ответственного слоя, данные тестов — в фабрики, сценарии — в параметризацию. jscpd с порогом дублирования 0 проверяет src и tests; минимальный обнаруживаемый блок — 5 строк и 50 токенов. Не обходить проверку переименованием переменных, исключениями или подавлениями.
- Слои presentation, application, domain, infrastructure не импортируют друг друга. Общие сообщения, DTO и интерфейсы (JSDoc) находятся в contracts. Только composition знает конкретные реализации; messaging реализует шину. Внутри слоя разрешены обычные вызовы. Реэкспорты, циклы, динамические импорты и вынос обходных вызовов в общий utils запрещены.
- Создавать и конфигурировать зависимости в контейнере composition; передавать потребителям через конструкторы/параметры. Не создавать HTTP-клиент, репозиторий или шину внутри компонента/обработчика. React Context допустим для передачи интерфейса шины на UI-границе, а не как глобальный service locator. Конкретная JS-библиотека DI и реализация шины выбираются при создании runtime; Python-библиотеки backend в браузер не переносятся.
- Взаимодействие слоев — только через шину: presentation → application → domain/infrastructure. API-вызовы, localStorage и прочий I/O принадлежат infrastructure. Domain выполняет чистые локальные преобразования; серверные расчеты метрик и прогноза не дублируются на клиенте.
- Одно пользовательское действие отправляет одну корневую команду. Начальная политика runtime, как на backend: не более 3 вызовов обработчиков суммарно на команду, включая последовательные и параллельные вложенные обращения и подписчиков событий; ответы не считаются переходами. Обратные и application → application вызовы запрещены. Реализация счетчика и тестов этой политики обязательна при подключении шины; текущие линтеры ее не проверяют.
- Не дробить команду на несколько корневых вызовов и не скрывать обращения в эффектах/таймерах ради обхода бюджета. Превышение требует пересмотра границ сценария; изменение лимита — отдельное обоснованное решение. Отдельным пользовательским действиям — отдельные контексты, никакого общего изменяемого счетчика асинхронных запросов.
- Применять паттерн «Репозиторий» к данным HTTP API/локального хранения: интерфейсы в contracts, реализации в infrastructure/repositories. Инжектировать репозиторий в обработчик infrastructure; application и компоненты обращаются к нему через шину. Детали fetch, DTO транспорта, кеширования и хранения не распространяются по слоям. Frontend не подключается напрямую к PostgreSQL; транзакции БД принадлежат backend.
- React-компоненты отвечают за отображение и пользовательский ввод. Соблюдать порядок Hooks и зависимости эффектов, избегать побочных эффектов при render. Состояние загрузки, ошибки, отмену запроса и защиту от устаревшего ответа тестировать явно. Использовать семантические элементы, доступные имена и управление с клавиатуры.
- Тестировать наблюдаемое поведение. Pure unit-тесты без сети, DOM и реального времени. Репозитории подменять fake/mock интерфейсов через DI; общие контрактные тесты использовать для fake и HTTP-реализации с тестовым транспортом. Компонентные тесты — через доступные роли и действия пользователя, а не приватные детали. Не ограничиваться снапшотами.
- При создании runtime добавить Vitest/Testing Library, тесты реального контейнера и шины, бюджета переходов, отмены и параллельных сценариев. Текущие Node-тесты проверяют сами инструменты качества; они не заменяют эти будущие тесты. E2E с backend — в корневом tests.
- Перед завершением изменений выполнить npm run check из frontend. Не ослаблять архитектурные контракты и не отключать правила без причины и регрессионного теста. На ревью проверять смысловую связность, скрытое I/O и правильность регистрации обработчиков: статический анализ не доказывает их отсутствие.
