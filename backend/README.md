# Backend: техническая основа

Бизнес-функции, FastAPI-приложение и БД еще не реализованы. Подключены инструменты качества, контейнер зависимостей и защищенный адаптер шины. Правила разработки — в [AGENTS.md](AGENTS.md).

## Запуск проверок

Из `backend/`, с установленным uv:

```sh
make setup
make format
make check
```

`make check` запускает isort, flake8, strict mypy, pylint (включая поиск дублирования), import-linter и pytest. GitHub Actions запускает те же команды для PR и main. `uv.lock` фиксирует зависимости; CI использует `--locked`. Форматирование не запускается автоматически в CI.

## Что взято из проекта-образца

Изучены `pyproject.toml`, `.pylintrc`, `Makefile`, `AGENTS.md`, `service/container.py`, `service/bootstrap.py`, `service/events/message_bus.py`, обработчики и тесты шины в `../gremion-projects/backend`.

Сохранены набор линтеров, лимит 120 символов, конструкторная инъекция через `dependency-injector==4.49.1` и механизм `mediapyr==0.1.6`: send/publish → зарегистрированный обработчик → provider → экземпляр из контейнера. Образец допускает прямые межслойные вызовы репозиториев и отключает duplicate-code; здесь эти послабления не применяются согласно требованиям проекта.

В отличие от глобального mediator и fallback `cls()` в образце, каждый контейнер получает собственную шину и Mediator с явным provider. Незарегистрированные зависимости не создаются неявно. Это сохраняет механизм библиотеки, устраняя общий реестр между тестами и обход DI. API интеграции проверен по [mediapyr](https://pypi.org/project/mediapyr/); подмена провайдеров соответствует [dependency-injector](https://python-dependency-injector.ets-labs.org/providers/overriding.html).

## Слои

| Каталог | Ответственность |
| --- | --- |
| `service/api` | HTTP-ввод/вывод; одна команда на действие |
| `service/application` | Обработчики пользовательских сценариев |
| `service/domain` | Чистые предметные расчеты и правила |
| `service/infrastructure` | Атомарные операции БД и внешние системы |
| `service/contracts` | Команды, события, DTO и интерфейс шины |
| `service/messaging` | Адаптер mediapyr, направления вызовов и бюджет |
| `service/container.py` | Создание зависимостей и будущая регистрация обработчиков |

Допустимый путь: API → application → domain/infrastructure. Ответ возвращается вызывающему обработчику и не считается новым переходом. Внутренние функции одного слоя вызываются напрямую. Контракты общие, не зависят от реализаций. Composition root — единственное исключение из запрета знания реализаций; это место сборки, а не слой бизнес-логики.

Для будущего обработчика объявить сообщение в contracts, класс с `async handle` в ответственном слое, provider в Container и зарегистрировать на полученной шине `bus.register(Message, Handler, container.handler, "application")`. Передавать provider без вызова: экземпляр создает контейнер при dispatch. Потребители получают интерфейс MessageBus через конструктор. Регистрацию делать один раз при bootstrap, не в router и не декораторами глобального mediator.

## Доступ к БД и тестирование репозиториев

Утвержден паттерн «Репозиторий» для всех операций с данными приложения. Интерфейсы размещаются в `service/contracts/repositories.py` или пакете `service/contracts/repositories/`, SQLAlchemy-реализации — в `service/infrastructure/repositories/`. Методы выражают операции предметной области, возвращают независимые DTO и скрывают SQL, ORM и устройство хранения. Реализация репозиториев запланирована вместе с подключением БД.

Путь вызова: API → шина → application → шина → persistence-обработчик infrastructure → репозиторий. Последний вызов остается внутри infrastructure и не добавляет межслойного перехода. Application и domain не получают репозитории напрямую: сохраняется обязательное взаимодействие слоев через шину.

DI-контейнер создает репозитории и фабрики сессий и инжектирует их в persistence-обработчики. Границей транзакции служит атомарная операция обработчика через Unit of Work: все ее репозитории используют одну сессию, commit/rollback выполняется централизованно. Независимый commit в методах репозитория запрещен. Миграции, управление транзакциями и технические healthchecks БД находятся вне этого правила доступа к данным приложения.

Для unit-тестов обработчиков использовать подмену интерфейса репозитория через provider.override: fake в памяти или mock. Не подменять внутренние цепочки SQLAlchemy. Для fake и реальной реализации подготовить общие контрактные тесты поведения; SQL, ограничения БД, конкуренцию и rollback проверять интеграционными тестами на PostgreSQL. Тесты application используют сообщения шины, а сквозной тест сценария сохраняет реальную шину и контейнер с подменой репозитория на нижней границе.

## Проверки связности и их пределы

Import-linter запрещает прямые и косвенные импорты между слоями, утечку контейнера/конкретной шины и зависимость предметных слоев от FastAPI/SQLAlchemy. Негативные тесты создают временный пакет с запрещенными импортами и проверяют отказ анализатора.

Шина считает фактические вызовы обработчиков в контексте корневого запроса, включая fan-out событий и последовательные обращения. Лимит 3 — начальная архитектурная политика для одного application-обработчика и максимум двух нижележащих операций. Обратные и однослойные dispatch запрещены независимо от лимита. Параллельные корневые запросы имеют независимые бюджеты. Лимит на события может остановить доставку после части обработчиков; это не механизм гарантированной доставки или отката.

Автоматика не измеряет смысловую связность, не находит любое похожее выражение и не защищает от намеренного обхода через динамический импорт, неверную регистрацию слоя или несколько отдельных корневых команд. Поэтому в ревью проверяются граф вызовов, отсутствие reflection/service locator, одна точка входа сценария и отсутствие знаний о чужих реализациях. Пока бизнес-обработчиков нет, проверки подтверждают каркас, а не качество будущих сценариев.
