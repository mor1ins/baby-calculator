# Backend

Реализована основа FastAPI: фабрика приложения, настройки окружения, единые ошибки, health/readiness, контейнер зависимостей и защищенный адаптер шины. Подключены SQLAlchemy/psycopg, начальная миграция PostgreSQL и проверка БД в readiness. Добавлены первые репозитории учетной записи/дневника и Unit of Work (B-03). Реализованы все 23 бизнес-операции принятого API, серверные сессии, расчеты и административный доступ. Правила разработки — в [AGENTS.md](AGENTS.md).

## Запуск проверок

Из `backend/`, с установленным uv:

```sh
make setup
make format
make check
```

`make check` запускает isort, flake8, strict mypy, pylint (включая поиск дублирования), import-linter и pytest. GitHub Actions запускает те же команды для PR и main, затем интеграционные тесты на PostgreSQL 16. `uv.lock` фиксирует зависимости; CI использует `--locked`. Форматирование не запускается автоматически в CI.

## Запуск приложения

Из `backend/`:

```sh
make setup
make run
# Либо с явными параметрами окружения и сервера:
BABY_ENVIRONMENT=dev uv run --locked uvicorn service.bootstrap:create_app --factory --host 127.0.0.1 --port 8000
```

`BABY_ENVIRONMENT`: `local` (по умолчанию), `dev`, `prod`, `test`. Недопустимое значение останавливает создание приложения. Пример — `.env.example`; файл `.env` автоматически не загружается, переменные передаются окружением процесса (в том числе через Compose). Настройки неизменяемы, создаются контейнером один раз на приложение. Импорт модулей не запускает приложение и не читает окружение.

| Маршрут | Поведение |
| --- | --- |
| `GET /health` | 200, `{"status":"ok"}`: HTTP-сервис отвечает. |
| `GET /ready` | 200, `{"status":"ready"}` при запущенном приложении, доступной БД и актуальной версии миграций; иначе 503 с общей ошибкой. |
| `GET /docs`, `GET /openapi.json` | Документация реализованных маршрутов в local/dev/test; отключена в prod. |

Readiness проверяет соединение (`SELECT 1`) и единственную ожидаемую ревизию `alembic_version` в пределах `BABY_DATABASE_TIMEOUT`. Отсутствие URL, недоступная БД, пустая схема, другая ревизия или таймаут дают 503 без деталей подключения. `/health` при этом продолжает отвечать 200. Проверка не подменяет тесты бизнес-функций. Технические маршруты не входят в публичный `/api/v1` и не расширяют 23 операции контракта. Автогенерируемая схема FastAPI перечисляет маршруты; полные тела запросов/ответов описаны в `../api/openapi.yaml`, по этому файлу валидируются входы и проверяются ответы в тестах.

Фабрика `service.bootstrap.create_app` собирает новый контейнер, регистрирует обработчики и инжектирует шину в HTTP-класс. Lifespan устанавливает/сбрасывает состояние запуска через `finally` и закрывает пул соединений при остановке. `/ready` проходит API → application → infrastructure за два вызова обработчиков; `/health` — простая HTTP-проверка без обращения к бизнес-слоям. Тесты readiness используют реальный mediator с бюджетом 2; в unit-тестах подменяется только обработчик БД. Контейнер не извлекается из request/state внутри обработчиков.

HTTP-ошибки, ошибки валидации и неожиданные исключения возвращают `{code, message, fields}` с `Cache-Control: no-store`. Сохраняются служебные заголовки `Allow`, `Retry-After`, `WWW-Authenticate`. Валидация указывает путь поля, но не отражает исходное значение. Неожиданные исключения возвращают нейтральный 500; текст исключения, тело запроса и пароли не включаются в ответ/сообщение логгера обработчика. Специфические ошибки предметной области будут подключены при реализации соответствующих сценариев.

Используются [lifespan FastAPI](https://fastapi.tiangolo.com/advanced/events/), [обработчики ошибок](https://fastapi.tiangolo.com/tutorial/handling-errors/) и [настройки Pydantic](https://docs.pydantic.dev/latest/concepts/pydantic_settings/). TestClient установленной Starlette использует `httpx2`, версии зафиксированы в `uv.lock`.

## Что взято из проекта-образца

Изучены `pyproject.toml`, `.pylintrc`, `Makefile`, `AGENTS.md`, `service/container.py`, `service/bootstrap.py`, `service/events/message_bus.py`, обработчики и тесты шины в `../gremion-projects/backend`.

Сохранены набор линтеров, лимит 120 символов, конструкторная инъекция через `dependency-injector==4.49.1` и механизм `mediapyr==0.1.6`: send/publish → зарегистрированный обработчик → provider → экземпляр из контейнера. Образец допускает прямые межслойные вызовы репозиториев и отключает duplicate-code; здесь эти послабления не применяются согласно требованиям проекта.

В отличие от глобального mediator и fallback `cls()` в образце, каждый контейнер получает собственную шину и Mediator с явным provider. Незарегистрированные зависимости не создаются неявно. Это сохраняет механизм библиотеки, устраняя общий реестр между тестами и обход DI. API интеграции проверен по [mediapyr](https://pypi.org/project/mediapyr/); подмена провайдеров соответствует [dependency-injector](https://python-dependency-injector.ets-labs.org/providers/overriding.html).

## Слои

| Каталог | Ответственность |
| --- | --- |
| `service/api` | HTTP-ввод/вывод; одна команда на действие |
| `service/application` | Обработчики пользовательских сценариев |
| `service/domain` | Чистые предметные расчеты и правила |
| `service/infrastructure` | Атомарные операции БД и внешние системы |
| `service/contracts` | Команды, события, DTO и интерфейс шины |
| `service/messaging` | Адаптер mediapyr, направления вызовов и бюджет |
| `service/container.py`, `service/bootstrap.py` | Создание зависимостей, регистрация обработчиков и жизненный цикл приложения |
| `service/settings.py` | Настройки окружения, доступные только composition root |

Допустимый путь: API → application → domain/infrastructure. Ответ возвращается вызывающему обработчику и не считается новым переходом. Внутренние функции одного слоя вызываются напрямую. Контракты общие, не зависят от реализаций. Composition root — единственное исключение из запрета знания реализаций; это место сборки, а не слой бизнес-логики.

Для будущего обработчика объявить сообщение в contracts, класс с `async handle` в ответственном слое, provider в Container и зарегистрировать на полученной шине `bus.register(Message, Handler, container.handler, "application")`. Передавать provider без вызова: экземпляр создает контейнер при dispatch. Потребители получают интерфейс MessageBus через конструктор. Регистрацию делать один раз при bootstrap, не в router и не декораторами глобального mediator.

## Доступ к БД и тестирование репозиториев

Утвержден паттерн «Репозиторий» для всех операций с данными приложения. Интерфейсы размещаются в `service/contracts/repositories.py` или пакете `service/contracts/repositories/`, SQLAlchemy-реализации — в `service/infrastructure/repositories/`. Методы выражают операции предметной области, возвращают независимые DTO и скрывают SQL, ORM и устройство хранения. В B-03 реализованы интерфейсы и SQLAlchemy-репозитории учетной записи/дневника, а также Unit of Work. Методы хранения для остальных сценариев добавляются вместе с соответствующими функциями A/S/D/M; подключение БД и миграции выполнены в B-02.

Путь вызова: API → шина → application → шина → persistence-обработчик infrastructure → репозиторий. Последний вызов остается внутри infrastructure и не добавляет межслойного перехода. Application и domain не получают репозитории напрямую: сохраняется обязательное взаимодействие слоев через шину.

DI-контейнер создает репозитории и фабрики сессий и инжектирует их в persistence-обработчики. Границей транзакции служит атомарная операция обработчика через Unit of Work: все ее репозитории используют одну сессию, commit/rollback выполняется централизованно. Независимый commit в методах репозитория запрещен. Миграции, управление транзакциями и технические healthchecks БД находятся вне этого правила доступа к данным приложения.

Для unit-тестов обработчиков использовать подмену интерфейса репозитория через provider.override: fake в памяти или mock. Не подменять внутренние цепочки SQLAlchemy. Для fake и реальной реализации подготовить общие контрактные тесты поведения; SQL, ограничения БД, конкуренцию и rollback проверять интеграционными тестами на PostgreSQL. Тесты application используют сообщения шины, а сквозной тест сценария сохраняет реальную шину и контейнер с подменой репозитория на нижней границе.

## Проверки связности и их пределы

Import-linter запрещает прямые и косвенные импорты между слоями, утечку контейнера/конкретной шины и зависимость предметных слоев от FastAPI/SQLAlchemy. Негативные тесты создают временный пакет с запрещенными импортами и проверяют отказ анализатора.

Шина считает фактические вызовы обработчиков в контексте корневого запроса, включая fan-out событий и последовательные обращения. Лимит 3 — начальная архитектурная политика для одного application-обработчика и максимум двух нижележащих операций. Обратные и однослойные dispatch запрещены независимо от лимита. Параллельные корневые запросы имеют независимые бюджеты. Лимит на события может остановить доставку после части обработчиков; это не механизм гарантированной доставки или отката.

Автоматика не измеряет смысловую связность, не находит любое похожее выражение и не защищает от намеренного обхода через динамический импорт, неверную регистрацию слоя или несколько отдельных корневых команд. Поэтому в ревью проверяются граф вызовов, отсутствие reflection/service locator, одна точка входа сценария и отсутствие знаний о чужих реализациях. Пока бизнес-обработчиков нет, проверки подтверждают каркас, а не качество будущих сценариев.

Контракты Command/Notification не наследуются от mediapyr: библиотека 0.1.6 использует тип сообщения как ключ реестра, без требования наследования в runtime. Типовая адаптация локализована в `messaging/bus.py`; отправка команд и fan-out событий проверяются на реальном mediator. Слои и contracts не могут импортировать bootstrap/settings в обход контейнера.

## PostgreSQL и миграции (B-02)

Поддерживаемая и проверенная версия для прототипа — PostgreSQL 16. Для `btree_gist` нужны права установки расширения (в управляемой БД его может предварительно установить администратор). URL берется только из `BABY_DATABASE_URL` в формате `postgresql+psycopg://…`; в настройках он хранится как SecretStr. Схема — [DATABASE.md](../api/DATABASE.md).

Начальная миграция `0001_initial` создает 13 таблиц, ограничения, индексы и роли `user`/`admin`. Аккаунт администратора, пароли и пользовательские данные не создаются. SQL зафиксирован рядом с файлом ревизии и не импортируется из изменяемых моделей приложения. В SQL есть только структурные ограничения; межстрочные правила предметной области, валидация IANA timezone и изменение версий ресурсов будут реализованы в атомарных операциях репозиториев по B-03 и последующим пунктам.

```sh
# Из backend/, после установки BABY_DATABASE_URL в окружении:
make migrate
uv run --locked alembic current
# Для просмотра SQL без изменения БД:
uv run --locked alembic upgrade head --sql
```

Приложение не запускает миграции автоматически. `make migrate` повторно безопасен: уже примененная ревизия не выполняется снова. Откат `alembic downgrade base` удаляет таблицы и данные приложения; предназначен для одноразовых тестовых БД. Расширение `btree_gist` сохраняется, поскольку его могут использовать другие схемы. Автоматический откат схемы при деплое не предусмотрен.

Контейнер создает отдельный async engine с пулом и `async_sessionmaker` для каждого приложения. Техническая проверка БД выполняется в infrastructure, не требует репозитория и не возвращает ORM-объекты в другие слои. Потребители бизнес-данных получают репозитории через Unit of Work. Сессии не разделяются между операциями; для каждой единицы работы фабрика создает новую сессию.

Для локальных интеграционных тестов можно запустить отдельную временную БД (Compose приложения относится к I-01):

```sh
docker run --detach --rm --name baby-test-postgres \
  --publish 127.0.0.1:55432:5432 \
  --env POSTGRES_USER=baby_test --env POSTGRES_PASSWORD=baby_test --env POSTGRES_DB=baby_test \
  postgres:16-alpine
# После готовности pg_isready:
BABY_TEST_DATABASE_URL=postgresql+psycopg://baby_test:baby_test@127.0.0.1:55432/baby_test make test-integration
docker stop baby-test-postgres
```

Тестовый пользователь должен иметь CREATEDB. Для каждого теста создается новая база со случайным именем, удаляемая в teardown; база из URL не очищается. Не использовать production-учетные данные. `make test-integration` требует URL и не допускает случайного зеленого результата из-за отсутствия настройки; `make check` запускает unit/архитектурные тесты без PostgreSQL. CI выполняет обе команды.

Проверены upgrade → повторный upgrade → downgrade → upgrade, отсутствие admin seed, разные состояния readiness, пересечения/нулевые интервалы, открытые сны, чужие связи/default, заметки без привязки и уникальность отмененных событий. Совместимость fake/PostgreSQL для текущих репозиториев и конкурентные конфликты проверены в T-01c; сценарии будущих функций получают собственные тесты.

Pylint проверяет также миграции; исключения ограничены штатными экспортируемыми Alembic-функциями (`context`, `op`) и обязательными именами метаданных ревизии. Запреты межслойных импортов и strict mypy сохранены.

## Репозитории и Unit of Work (B-03)

Контракты — `service/contracts/repositories.py`, DTO и внутренняя команда записи — `service/contracts/persistence.py`. SQLAlchemy-реализации расположены в `service/infrastructure/repositories/`; они используют параметризованный SQL через AsyncSession, возвращают неизменяемые dataclass DTO и не вызывают commit. Парольный хеш принимается только во внутреннем NewAccount, исключен из repr и не возвращается в Account.

Минимальные методы основы:

- AccountsRepository: создать запись пользователя с ролью user, прочитать по ID, изменить имя с ожидаемой версией. Нормализация email, хеширование паролей и публичная регистрация относятся к A-01.
- DiariesRepository: создать дневник, прочитать его по ID владельца. Выбор владельца для пользовательского запроса в дальнейшем берется из проверенной сессии, а не из произвольного ввода клиента.
- UnitOfWork: доступ к обоим репозиториям внутри async-контекста и явный commit. Выход без commit всегда откатывает изменения; контекст одноразовый, после commit/выхода репозитории недоступны. Ошибка SQL или конфликт версии делает транзакцию непригодной для последующего commit.

DI-контейнер создает фабрики сессии, транзакционного контекста, репозиториев и UoW. Все репозитории одной операции используют одну сессию. Persistence-обработчик получает только интерфейс UnitOfWork; конкретные фабрики и SQL остаются в infrastructure/composition. При отсутствии настройки БД создание фабрики сессий завершается явной ошибкой.

Внутренний `CreateAccountDiaryHandler` атомарно сохраняет пользователя, роль user и дневник. Публичного маршрута регистрации он не создает. В тесте application-обработчик вызывает его через реальный mediator: API → application → infrastructure, бюджет 2. SQL и типы сессии не передаются через шину. Прямой вызов этой команды из API отклоняется проверкой направления.

В `tests/fakes/repositories.py` есть fake UoW и репозитории для последовательных unit-тестов. Fake хранит только нужные текущим контрактам DTO, имитирует транзакционный снимок, commit/rollback и базовые конфликты; это не полная эмуляция PostgreSQL, его проверок полей или блокировок. Одни и те же тесты в `test_repositories.py` выполняются с fake и SQLAlchemy-реализацией на мигрированной PostgreSQL.

Проверены явный commit, rollback без commit/при ошибке/отмене, откат пользователя при ошибке дневника, дубли, конфликт версии, запрет записи после ошибки, срок жизни репозитория и повторный запуск новой команды после rollback. Отдельный PostgreSQL-тест проверяет параллельные команды в одном контейнере и атомарный конфликт двух обновлений одной версии. Негативные проверки и дополнительные конкурентные сценарии текущих репозиториев выполнены в T-01c; ограничения будущих функций проверяются вместе с их реализацией.

## Негативные контракты и отказ транзакции (T-01c)

Общие сценарии fake/PostgreSQL расширены проверками пустых/слишком длинных имен и email, ненормализованного email, пустого timezone, недопустимого default, дублей ID/владельца дневника и обновления отсутствующего пользователя. У fake устранены расхождения с этими ограничениями БД и ошибками жизненного цикла. PostgreSQL `DataError` (например, превышение длины varchar), как и `IntegrityError`, преобразуется в безопасный PersistenceConflict и запрещает commit текущей транзакции.

Проверки используют общие фабрики и фикстуры, без копирования сценариев между реализациями. Fake остается инструментом последовательных тестов текущих репозиториев: он не воспроизводит блокировки PostgreSQL, все его типы и правила будущих графиков/снов.

Дополнительные тесты на настоящем PostgreSQL:

- Отложенный constraint trigger, созданный только в одноразовой тестовой БД, отклоняет запись при commit после успешных INSERT пользователя и дневника. Обе записи отсутствуют после отката; следующая команда через тот же контейнер/шину успешно сохраняется.
- Одновременное создание с одинаковым email или ID дневника дает ровно одного победителя; проигравшая транзакция не оставляет пользователя или дневник.
- Незавершенная запись не видна другой единице работы; после commit становится видимой.

Результат: `make check` — 51 тест плюс все линтеры/архитектурные проверки; `make test-integration` — 38 тестов на PostgreSQL 16. Проверен явный отказ сервера при commit. Потеря соединения во время commit может оставлять результат неизвестным; такие записи нельзя автоматически повторять как гарантированно откатившиеся.


## Бизнес-операции прототипа

Реализованы все 23 операции [API-контракта](../api/README.md). Запросы проверяются по исходному OpenAPI, включая запрет лишних полей. Сессии и лимиты попыток входа/регистрации хранятся в PostgreSQL, пароли — Argon2id. CSRF обязателен для записей, Origin проверяется по `BABY_PUBLIC_ORIGIN`; cookie Secure в dev/prod и HttpOnly во всех окружениях.

`Operation` → application → `PersistOperation` — атомарная операция репозитория с общей транзакцией. Чтение/назначение дня дополнительно обращается в domain за расчетом; бюджет остается 3. `service/wiring.py` — часть composition root: собирает scope репозиториев, остальные слои не имеют доступа к нему. SQL находится только в `infrastructure/repositories`. Блокировка аккаунта сериализована с пользовательскими записями; версии/заметки/снимки меняются в общей транзакции.

Схема состоит из начальной миграции, `0002_auth_limits` (общий лимит аутентификации) и `0003_target_move` (отложенный FK для атомарного переноса сна между днями). Время передается в расчет явно; длительности считаются по абсолютным моментам. Ночные отметки не меняют длительность сна.

Интеграционные API-тесты проверяют ответы по OpenAPI, права двух пользователей, admin, блокировку/разблокировку, CSRF, версионные/конкурентные конфликты, снимки графиков, перенос сна, заметки, DST и идемпотентность событий. Для всех публичных операций отдельно проверяется точный бюджет реальной шины/контейнера с подменой репозитория. E2E находятся в корневом `tests`.

Полный запуск и ручное создание администратора: [корневой README](../README.md). Вне контейнера используется `BABY_DATABASE_URL=… .venv/bin/python ../deploy/create_admin.py --email admin@example.com` из backend; пароль вводится интерактивно.

## Диагностика ошибок API

Ошибки API пишутся в stderr как JSON с `event=api_error`: метод, шаблон маршрута,
HTTP-статус, код ошибки, тип исключения и `request_id`. Этот же ID возвращается
в заголовке `X-Request-ID`. Бизнес-ошибки содержат `reason`; ошибки времени сна —
`time_errors` с причиной `future` или `not_after_start`.

После проверки входного запроса `context` содержит имя операции, точное серверное
`server_now` (UTC) и версию. Для `createSleep`/`updateSleep` дополнительно записываются
переданные `day`, `kind`, `start`, `end`, `ends_night` и ID изменяемого сна. При PATCH
в журнал попадают только переданные поля. Сравнение `start`/`end` с `server_now`
позволяет обнаружить опережение часов клиента. Отклоненные до проверки схемы тела
не записываются. Cookie, токены, пароли, заметки и строки запроса не журналируются.
Для ошибок 500 записываются тип исключения и кадры стека (файл, строка, функция),
без значений локальных переменных и текста исключения.

Чтение локальных ошибок: `docker compose logs --timestamps --since=1h backend | rg api_error`.
Изменение логирования не восстанавливает параметры старых запросов.

Допуск опережения часов клиента задаётся `BABY_CLOCK_SKEW_TOLERANCE_MINUTES`
(целое число минут, по умолчанию `20`; `0` включает строгую проверку).
Начало/конец сна и ночные отметки принимаются, если опережение строго меньше
допуска; ровно 20 минут при стандартной настройке уже отклоняются. Переданное
время сохраняется без округления или подмены. Порядок границ сна, пересечения
и попадание отметок внутрь сна проверяются как прежде.
Для Docker Compose установите переменную в корневом `.env` (на сервере — `.env`
окружения) и примените `docker compose up -d --no-deps backend`. При запуске
без Docker передайте переменную окружения процессу backend и перезапустите его.
