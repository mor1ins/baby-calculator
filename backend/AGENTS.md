# Правила backend

Обязательны для кода и тестов в этом каталоге. Подробности и команды — в README.md.

- Стиль образца `gremion-projects/backend`: 4 пробела, строка до 120 символов, snake_case для функций/модулей, PascalCase для классов, UPPER_CASE для констант. isort, flake8, mypy и pylint обязательны; новые публичные функции типизированы.
- Не копировать блоки логики. Общие вычисления выносить в чистые функции внутри ответственного слоя, повторяемые тестовые данные — в фикстуры/фабрики, сценарии — в параметризацию. Не создавать общий helpers-модуль, связывающий реализации разных слоев. Pylint duplicate-code включен; не отключать его ради зеленого CI.
- Зависимости создавать и конфигурировать в `service/container.py` через dependency-injector. Инжектировать через конструктор; FastAPI Depends допускается только на входной границе при будущем подключении API. Не обращаться к контейнеру из обработчиков, не использовать service locator, глобальные сессии или создание зависимостей внутри потребителя.
- Слои `api`, `application`, `domain`, `infrastructure` не импортируют друг друга, в том числе через реэкспорты и относительные импорты. Обмен — исключительно через MessageBus и типы в `contracts`. Внутри одного слоя обычные вызовы разрешены.
- Только composition root знает конкретные обработчики и связывает их с providers.Factory/Singleton/Resource. mediapyr скрыт адаптером messaging; импортировать глобальный mediator запрещено. Регистрация обработчиков — при сборке приложения, до обработки запросов.
- API отправляет одну команду/запрос application на пользовательское действие. Application владеет сценарием; domain выполняет чистые расчеты, infrastructure выполняет I/O. Application может послать сообщение domain или infrastructure; обратные вызовы и application → application запрещены. DTO не содержат ORM-объекты, сессии или сервисы.
- На корневую команду бюджет по умолчанию — 3 вызова обработчиков: API → application и до двух обращений к domain/infrastructure. Считаются все последовательные обращения и подписчики событий, а не только глубина. Превышение — архитектурная ошибка. Не дробить сценарий на несколько корневых команд, не использовать фоновые задачи для обхода бюджета.
- Если бюджет недостаточен, сначала проверить размер команды, N+1, зависимости от деталей хранения и возможность одной атомарной операции infrastructure. Не повышать общий лимит автоматически. Исключение требует описания трассы и причины в PR, отдельного решения и теста с конкретным бюджетом.
- Доступ к данным приложения в БД обязателен через паттерн «Репозиторий»: интерфейсы в `service/contracts/repositories.py` (или одноименном пакете), реализации SQLAlchemy в `service/infrastructure/repositories/`. SQL-запросы и преобразование ORM в независимые DTO инкапсулированы в реализации репозитория; обработчики не выполняют SQL и не получают ORM-объекты или сессии. Миграции, управление транзакциями и технические проверки доступности БД не являются операциями репозитория.
- Репозитории и фабрики сессий собираются в DI-контейнере. Интерфейс репозитория инжектируется только в persistence-обработчик infrastructure; api/application/domain обращаются к нему через сообщения шины, а не вызывают репозиторий напрямую. Прямой вызов репозитория внутри infrastructure не является межслойным переходом.
- В unit-тестах persistence-обработчиков подменять репозиторий in-memory fake или mock его интерфейса через DI, не мокать цепочки SQLAlchemy. Общие контрактные тесты запускать для fake и PostgreSQL-реализации; специфические ограничения, конкурентный доступ и транзакции проверять на PostgreSQL. Каждому тесту — изолированные данные и свежие подмены.
- Ошибка шины не откатывает уже выполненные изменения: транзакции должны принадлежать атомарному persistence-обработчику через инжектируемую единицу работы (Unit of Work). Репозитории одной операции используют общую сессию; commit/rollback выполняет единица работы, репозитории не делают независимый commit. Не имитировать транзакцию последовательностью команд save/update. mediapyr — внутрипроцессная шина, не надежная очередь; долговечные события требуют отдельного решения с outbox.
- Тестировать поведение, не приватные поля. Unit-тесты расчетов без БД и сети; интеграционные тесты SQL — с PostgreSQL, не SQLite. Часы и I/O инжектируются. Подмены через provider.override или фейки контрактов; тесты не зависят от порядка и глобального состояния.
- Для каждой команды добавить тест числа обращений через реальную шину и контейнер, проверку результата/ошибок; для новых границ — негативный тест обхода. Не мокать шину в единственном тесте сценария. Проверять параллельность, очистку контекста после ошибок и изоляцию контейнеров.
- Backend-тесты хранить в `backend/tests` с отражением структуры модулей; корневой `tests` предназначен для будущих межсервисных/E2E-тестов.
- Перед завершением изменений выполнить `make check` в backend. Не ослаблять контракты импортов, типизацию и лимиты без обоснования. Динамические импорты, reflection и getattr для обхода слоев запрещены; статический анализ не доказывает их отсутствие, это также предмет ревью.
