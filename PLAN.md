# План переработки калькулятора сна и бодрствования

Статус: рабочий локальный прототип реализован. Все 23 API-операции, мобильные экраны, PostgreSQL, миграции и Docker Compose работают совместно. Пользователь утвердил выполнение оставшихся задач без согласования каждого пункта, до рабочего локального прототипа. Внешний выпуск ожидает выбора VPS/домена и настройки секретов; конфигурация dev/prod и GitHub Actions подготовлена.


## 1. Цель и границы

Перейти от однодневного калькулятора в браузере к многопользовательскому дневнику с постоянным хранением истории, персональными графиками и прогнозом текущего дня.

Обязательные возможности первой версии:

- Самостоятельная регистрация, вход и выход; роли `user` и `admin` с возможностью расширения.
- Хранение данных пользователя за произвольное число дней в PostgreSQL.
- Ввод только фактических интервалов сна; вычисление бодрствования между ними.
- Комментарии к интервалам сна и вычисленным интервалам бодрствования.
- Быстрая отметка ночного пробуждения/плача одним нажатием, счётчик и журнал событий за сон, отмена ошибочной отметки.
- Несколько персональных графиков и выбор графика для конкретного дня.
- Главная страница: текущий день, факты, текущий интервал, прогноз и метрики.
- Метрики дневного сна, ночного сна и дневного бодрствования.
- Администратор видит всех пользователей и их сохраненные данные, но не редактирует дневники, графики и комментарии. Отдельное разрешенное действие — блокировка учетной записи.
- Учетная запись администратора создается вручную в БД, без публичной регистрации администратора.
- Контейнерное развертывание через GitHub Actions, отдельные окружения `dev` и `prod`.

Утвержденные ограничения первой версии (подтверждены пользователем 3 октября 2026 года):

- Один дневник ребенка на пользователя.
- Русский интерфейс.
- Без совместного доступа родителей.
- Без уведомлений.
- Без медицинских рекомендаций.
- Без переноса старых данных: новая версия начинает работу с пустыми дневниками, импорт/экспорт для миграции из старого калькулятора не разрабатывается.
- В прототипе нет резервного копирования, включая окружение `prod`; сроки хранения копий и цели восстановления для него не задаются. Решение о резервном копировании для последующих версий принимается отдельно.

В `deploy` находятся контейнеры, серверная конфигурация и инструкции, в корневом `tests` — Playwright E2E. Backend и frontend реализованы и проверяются линтерами, архитектурными, unit- и интеграционными тестами. Метаданные `.git` оставлены в корне. В корне создан новый `.gitignore`; прежний сохранен в архиве без изменений. Локальные `node_modules`, `dist` и файлы сборки тоже перенесены и остаются игнорируемыми.

Старая версия запускается из `only_web_version`: `npm ci`, затем `npm run dev`. Ее исходный `base` для GitHub Pages сохранен. Перенесенный `only_web_version/.github/workflows/deploy.yml` больше не является активным workflow GitHub Actions. Уже опубликованный сайт этим переносом не удаляется. Будущие workflow новой версии должны находиться в корневом `.github/workflows/`, а не в `deploy/`.

В старой версии данные находятся в `localStorage` браузера. Утвержден отказ от их переноса: новая версия начинает работу с пустыми дневниками. Совместимость со старым форматом и миграционный импорт/экспорт не требуются. Архив исходников в `only_web_version` сохраняется.

## 3. Предлагаемая архитектура и стек

Один backend с модулями авторизации, пользователей, дневника, графиков, расчетов и администрирования. Frontend обращается к REST API `/api/v1`. Расчеты на backend являются единым источником результата; frontend отображает их и обновляет текущие счетчики.

| Область | Решение | Назначение |
| --- | --- | --- |
| Backend | Python, FastAPI, Uvicorn, Pydantic | HTTP API, валидация, OpenAPI |
| Данные | PostgreSQL, SQLAlchemy, psycopg, Alembic | Хранение, транзакции и версионируемые миграции |
| Frontend | React, JavaScript, Vite | SPA; TypeScript можно согласовать отдельно, он уже есть в архиве |
| Работа с API | TanStack Query, React Router | Серверное состояние, маршрутизация |
| Формы | React Hook Form | Ввод сна, графиков и учетных данных |
| Авторизация | Серверные сессии в PostgreSQL, HttpOnly cookie | Отзыв доступа при выходе и блокировке |
| Пароли | Argon2id через поддерживаемую библиотеку | Хранение только хешей |
| Проверки | pytest, HTTPX; Vitest, Testing Library; Playwright | Расчеты, API, компоненты, пользовательские сценарии |
| Качество | isort, flake8, mypy, pylint, import-linter; ESLint, Prettier, Stylelint, dependency-cruiser, jscpd | Стиль образца, типизация, дублирование и изоляция слоев |
| Доставка | Docker, Docker Compose, GitHub Actions, GHCR | Сборка и публикация образов, развертывание |
| Входящий трафик | Nginx и HTTPS | Статика frontend и проксирование `/api` |

Версии зависимостей и базовых образов выбираются и фиксируются при инициализации новой версии. Для Python — `pyproject.toml` и lock-файл uv; для frontend — npm и `package-lock.json`. Redis и очередь задач пока не требуются.

FastAPI допускает выбор ORM; SQLAlchemy здесь — проектное предложение ([документация FastAPI](https://fastapi.tiangolo.com/tutorial/sql-databases/)). Доставка рассчитана на GitHub Free, включая приватный репозиторий: отдельные workflow и repository secrets с префиксами `DEV_`/`PROD_`, без обязательных GitHub Environments. В приватных репозиториях Free Environments недоступны ([документация GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)).

Backend разделен на `api`, `application`, `domain`, `infrastructure`; взаимодействие слоев — через контракты и `mediapyr`, зависимости собираются в `dependency-injector`. Для доступа к БД утвержден паттерн «Репозиторий»: интерфейсы в `contracts`, реализации в `infrastructure/repositories`, инъекция в persistence-обработчики через контейнер. Остальные слои обращаются к данным через шину. Атомарность обеспечивает инжектируемый Unit of Work с общей сессией и централизованным commit/rollback. Конкретные правила, запреты импортов и бюджет переходов закреплены в `backend/AGENTS.md`.

## 4. Правила предметной области

Правила, закрепленные в принятом API-контракте, утверждены для первой версии. Числовые примеры прогноза утверждены в [api/FORECAST_EXAMPLES.md](api/FORECAST_EXAMPLES.md); при реализации расчетов их необходимо покрыть тестами T-05.

### 4.1. Время, день и история

- Хранить начало и конец сна как абсолютные моменты времени (`timestamptz`), часовой пояс дневника — идентификатор IANA, например `Europe/Moscow`.
- В интерфейсе вводить дату и время, чтобы сон через полночь не требовал догадок.
- Днем дневника считаем цикл от окончательного утреннего пробуждения до следующего окончательного утреннего пробуждения. Дата дня — локальная дата начала цикла; ночной сон относится к дню, после которого он начался.
- Вчерашний ночной сон показывать утром как контекст, не прибавляя его повторно к метрикам сегодняшнего цикла.
- Окончательное утреннее пробуждение определяется завершением последнего отрезка ночного сна с признаком завершения ночи. Это уточнение записи сна, а не ручной ввод бодрствования.
- Измеренные периоды ночного бодрствования задаются разрывами между отрезками ночного сна одной ночи. Эти разрывы не входят в дневное бодрствование. Короткое пробуждение/плач можно отдельно отметить одним нажатием без указания длительности: такая отметка не завершает сон и не создает разрыв.
- Если граница дня неизвестна, показывать неполноту данных, а не считать отсутствие записей подтвержденным бодрствованием. Для первого дня достаточно внести предшествующий ночной сон и его окончание.
- Длительности считать по абсолютному времени, включая смену часового пояса и переходы летнего времени. Часовой пояс прошедшего дня сохранять, чтобы смена настроек не перемещала историю.

### 4.2. Фактические интервалы и комментарии

- Сон: начало, конец (может отсутствовать у текущего сна), тип `дневной` / `ночной`, комментарий.
- Пользователь может добавлять, исправлять и удалять собственные записи, в том числе за прошлые дни.
- Не более одного незавершенного сна на дневник; пересечения запрещены, конец строго позже начала. Проверять конфликты и при одновременных запросах.
- Реальные будущие интервалы не создавать: будущее принадлежит прогнозу. Соседние интервалы могут касаться границами; нулевое бодрствование не показывается.
- Бодрствование вычисляется как промежуток между окончанием одного сна и началом следующего; текущий промежуток — до текущего времени. Ночные разрывы отмечаются отдельно.
- Комментарии к вычисляемому бодрствованию хранить отдельно, с привязкой к ID соседних снов, а не к порядковому номеру на экране. Для текущего бодрствования допускается незаполненная правая граница; при появлении следующего сна она закрепляется.
- После исправления времени соседних снов комментарий сохраняется. Если удаление или вставка сна разрушает промежуток, комментарий сохраняется как требующий перепривязки; пользователь решает, к чему его привязать. Молчаливое удаление недопустимо.
- Для прогнозных интервалов комментарии в первой версии не предусмотрены: они еще не являются записями дневника. Для фактического или текущего интервала доступна одна редактируемая заметка.

### 4.2.1. Быстрые отметки ночных событий

- Во время ночного сна крупная кнопка «Проснулся / заплакал» сразу добавляет одну отметку с временем события и устойчивым ID сна. Повторное засыпание не требует отдельного нажатия.
- Рядом показывать число отметок за этот сон, время последней и журнал всех событий с датами, включая переход через полночь.
- «Отменить последнюю» удаляет конкретную последнюю отметку; в журнале можно удалить любую ошибочную. Итог всегда вычисляется по актуальному списку событий.
- Не завершать сон, не менять его начало/конец, метрики длительности и прогноз автоматически. Это частота отмеченных эпизодов, не измерение длительности ночного бодрствования и не медицинская оценка.
- После окончательного завершения сна быстрый ввод скрывается, журнал и счётчик сохраняются. Окончание ночи — отдельное явное действие.
- В истории и административном просмотре показывать счётчик и журнал. Администратор не может добавлять и удалять события.
- При редактировании сна сохранять связь по ID. Если событие осталось вне новых границ, явно предложить исправить границы или удалить ошибочную отметку; не терять события молча.
- В продукте сохранять события в БД через репозиторий. Создание должно быть идемпотентным по ID клиентского действия: повтор HTTP-запроса не увеличивает счётчик, отдельные нажатия — отдельные события. При ошибке сохранения не показывать успешную синхронизацию.

### 4.3. Графики

График — именованный шаблон последовательности длительностей. У пользователя может быть несколько шаблонов, например «Обычный день» и «Во время болезни». Графики доступны в отдельном разделе и через переключатель на странице дня.

Пример пользовательского графика:

| Интервал | Длительность |
| --- | --- |
| Бодрствование 1 | 4:20 |
| Дневной сон 1 | 1:20 |
| Бодрствование 2 | 4:40 |
| Дневной сон 2 | 0:20 |
| Бодрствование 3 | 3:00 |
| Ночной сон | 10:00 |

В примере дневной сон — **1:40**, дневное бодрствование — **12:00**, ночной сон — **10:00**, весь цикл — **23:40**. Не дополнять автоматически до 24 часов: показывать сумму и отклонение, разрешать сохранить такой график.

- Длительности — положительное целое число минут; отображение `ч:мм`.
- Последовательность: бодрствование и дневной сон чередуются, последнее дневное бодрствование завершается ночным сном. Допускается день без дневных снов.
- Шаблоны можно создавать, переименовывать, копировать, изменять и архивировать; один можно назначить по умолчанию.
- Для дня сохраняется снимок выбранного графика. Изменение или архивирование шаблона не меняет историю.
- При сохранении изменений шаблона пользователь выбирает «Начиная с сегодняшнего дня» (обновить шаблон и явно заменить сегодняшний снимок) или «Для следующих дней» (обновить только шаблон). Сегодня определяется в часовом поясе дневника. Существующие снимки будущих дней сохраняются; новые дни используют обновленный шаблон, если он выбран по умолчанию или назначен явно. Сам выбор режима не меняет график по умолчанию. Фактические сны не меняются.
- Замена графика конкретного дня меняет только его план и прогноз, сохраняя фактические записи. Пока график не выбран, факты и метрики доступны, прогноз отсутствует.

### 4.4. Метрики и прогноз

- Дневной сон: сумма фактических длительностей дневных снов выбранного цикла.
- Ночной сон: сумма отрезков ночного сна, относящихся к этому циклу, за вычетом только явно записанных разрывов. Быстрые отметки пробуждения/плача не имеют длительности и не вычитаются из времени сна.
- Дневное бодрствование: сумма промежутков от утреннего пробуждения до начала ночи за вычетом дневных снов; ночные пробуждения исключаются.
- Для текущего интервала показывать прошедшую длительность отдельно от завершенных интервалов; итог «на сейчас» может включать ее с явной отметкой. Прогноз не входит в фактические метрики.
- API возвращает признак полноты данных: неизвестное значение не подменяется нулем.
- Прогноз строится от фактического утреннего пробуждения, затем корректируется после каждого фактического сна по последовательности выбранного графика.
- Дневные сны сопоставляются с планом по порядку; завершенные интервалы всегда остаются фактическими. Будущие длительности берутся из снимка графика.
- Для текущего интервала ожидаемый конец = его фактическое начало + плановая длительность. Если это время уже прошло, показывать превышение; дальнейшую временную линию считать от текущего времени и помечать условной до фактического окончания интервала.
- Показывать ближайшее укладывание/пробуждение, предполагаемое начало ночи и следующий утренний подъем.
- При лишнем дневном сне после исчерпания плана применять последнее плановое дневное бодрствование и показывать расхождение. При пропущенном сне не угадывать намерение: пользователь выбирает другой график либо фиксирует начало ночи, которое завершает дневной прогноз.
- Пересчитывать после добавления, изменения, удаления сна, смены графика и обновления текущего времени. Для прошлых завершенных дней отображать факты и сохраненный план.

## 5. Пользователи и права

| Действие | user | admin |
| --- | --- | --- |
| Просмотр своего дневника и графиков | Да | Если есть собственный дневник и право пользователя |
| Изменение своего дневника и графиков | Да | Только при отдельном праве пользователя |
| Просмотр всех пользователей и их данных | Нет | Да, только чтение |
| Изменение чужих снов, графиков и комментариев | Нет | Нет |
| Блокировка/разблокировка обычного пользователя | Нет | Да |
| Назначение ролей через публичный API | Нет | Нет в первой версии |

- Роли хранить в таблицах `roles` и `user_roles`; проверки строить вокруг разрешений, с запретом по умолчанию. Новая роль не должна требовать изменения enum в БД.
- Регистрация всегда назначает только `user`, поля роли и блокировки не принимаются от клиента.
- Проверять владельца объекта на backend при каждом доступе, включая вложенные ресурсы и выбор чужого шаблона.
- У администратора отдельные маршруты чтения и отдельное действие смены статуса пользователя; универсального административного редактирования данных нет.
- Блокировка запрещает вход и доступ к API, отзывает активные сессии, сохраняет дневник. Блокировка администраторов и самого себя запрещена на уровне API.
- Сессии: случайный непрозрачный токен, в БД его хеш, срок действия и отзыв. Cookie `HttpOnly`, `Secure`, `SameSite`; CSRF-защита изменяющих запросов. Пароли и токены исключить из логов и API-ответов.
- Ограничить частоту попыток входа и регистрации; возвращать понятные ошибки без раскрытия чужих данных.
- Подготовить инструкцию ручного создания admin: генерация хеша штатной библиотекой, транзакционная вставка пользователя и роли в БД, проверка входа. Без фиксированного пароля в миграциях, автоматического admin seed и endpoint создания admin.
- Журналировать блокировки/разблокировки с исполнителем, временем и причиной.

## 6. Схема данных

Схема подготовлена в [api/DATABASE.md](api/DATABASE.md): таблицы, поля, связи, ограничения, индексы, диаграмма и правила транзакций. API-контракт остается источником публичных форматов; DATABASE.md определяет их хранение.

Основные группы: пользователи/роли/сессии, дневники/шаблоны/снимки дней, сны/ночные события, привязки интервалов/комментарии, административный аудит. `interval_targets` сохраняет идентичность вычисленных промежутков без хранения длительностей бодрствования. Удаленные ночные события сохраняют ID для защиты от запоздавших повторов. Метрики, полнота дня, границы цикла и прогноз вычисляются из фактов.

Изоляция владельцев обеспечивается проверками доступа и составными внешними ключами; отсутствие пересечений — PostgreSQL exclusion constraint. Записи выполняются через репозитории в одной единице работы с проверкой версий и обновлением всех затронутых дней. Миграции и базовые проверки ограничений на PostgreSQL реализованы в B-02. Основа репозиториев учетной записи/дневника и Unit of Work реализована в B-03; методы остальных сценариев добавляются в A/S/D/M. Негативные контракты текущих репозиториев, сбои commit и конкурентные конфликты проверены в T-01c; при добавлении новых операций тесты расширяются.

## 7. Интерфейс и API

Основные экраны: регистрация/вход; «Сегодня»; история с выбором даты; «Мои графики» с редактором; настройки часового пояса; список пользователей администратора; просмотр выбранного дневника администратором без кнопок изменения.

Главный экран адаптировать для телефона: переключатель даты и графика, три метрики, временная линия с различимыми фактом/текущим состоянием/прогнозом, добавление и завершение сна, комментарии. Предусмотреть состояния загрузки, отсутствия данных, неполной истории, ошибок и блокировки учетной записи.

Дизайн первой версии в `design/` принят. Контракт frontend/backend принят пользователем и зафиксирован в [api/openapi.yaml](api/openapi.yaml); правила взаимодействия и перечень операций — в [api/README.md](api/README.md). Это источник истины для реализации и интеграционных тестов. Контракт не является реализацией сервера.

Минимальный API использует `/api/v1`, JSON и cookie-сессии с CSRF-защитой. Один ответ дня включает сон, временную линию, заметки, ночные события, метрики и прогноз. Бодрствование и расчеты формирует backend. Исправление сна защищено версиями; повтор ночной отметки с тем же ID не создает дубль. Admin читает чужие данные и меняет только статус блокировки.

История запрашивается диапазонами до 31 дня, пользователи — с курсорной пагинацией. Ошибки имеют единый формат. Административные ответы не содержат хешей паролей, токенов и секретов. Структура контракта и JSON-примеры проверяются в CI; проверка фактических прав, транзакций и расчетов остается задачей реализации.

## 8. Окружения и доставка

- Локальная разработка: Compose для PostgreSQL и приложения; отдельные команды установки зависимостей, миграций и тестов.
- Утверждено: один VPS для `dev` и `prod`, развертывание через Docker Compose. Окружения используют отдельные Compose-проекты, контейнеры приложения и PostgreSQL, сети, volumes и учетные данные. Отказ VPS затрагивает оба окружения.
- Утверждена схема доменов: основной домен для `prod`, поддомен `dev` для разработки. В каждом окружении frontend и API работают на одном origin; API доступен через `/api/v1`. Конкретное доменное имя пока не выбрано, его необходимо определить до настройки DNS и HTTPS.
- Утверждена адаптация под GitHub Free: отдельные workflow dev/prod и repository secrets с префиксами `DEV_`/`PROD_`, без GitHub Environments и их правил подтверждения. Ручной выпуск prod запускается через `workflow_dispatch`. Префиксы секретов обозначают назначение, но сами по себе не ограничивают доступ workflow к ним. Данные prod не копировать в dev без отдельной процедуры обезличивания.
- Утверждена доставка по SSH из GitHub Actions: VPS скачивает выбранные образы из GHCR по digest, запускает миграции и обновляет нужный Compose-проект. Сборка образов выполняется в CI, а не на VPS.
- Утверждена возможность деплоя из pull request в общее окружение `dev`. Утвержден ручной запуск через GitHub Actions с указанием номера открытого PR, после успешных проверок выбранного коммита. Деплой заменяет текущую версию dev; отдельное окружение для каждого PR в первой версии не создается.
- Для PR-деплоя фиксировать точный SHA исходного коммита и использовать результаты проверок и образы именно этого SHA. При обновлении PR новая версия требует нового запуска. Деплои dev выполнять последовательно, без одновременного применения миграций. Не выдавать секреты VPS коду недоверенных PR; управляющий workflow брать из основной ветки.
- Утвержден порядок выпуска: merge в `main` → автоматический deploy в dev; выбранная версия, проверенная в dev → ручной deploy в prod через GitHub Actions.
- Собирать образы frontend/backend один раз, отмечать SHA коммита и продвигать те же digest из dev в prod. Не использовать `latest` как единственный идентификатор релиза.
- Секреты — в GitHub repository secrets/на сервере, примеры конфигурации без значений — в `.env.example`. БД не публиковать в интернет.
- Миграции запускать отдельным шагом до приложения, исключить параллельные миграции. Предпочитать совместимые миграции; автоматическое резервное копирование в прототипе не предусмотрено.
- После деплоя проверять readiness API, доступность БД и основной сценарий. При неуспехе — остановка продвижения и возврат предыдущего образа; откат схемы БД планируется отдельно и не подразумевается автоматически.
- Резервное копирование PostgreSQL и проверки восстановления копий исключены из прототипа по решению пользователя. Подготовить логи, healthchecks, ротацию логов и минимальные оповещения о недоступности.
- Размещение на одном VPS и схема доменов утверждены; доставка по SSH из GitHub Actions с GHCR утверждена. Выбор конкретного VPS/провайдера отложен пользователем до настройки деплоя; доменное имя также выбирается перед настройкой DNS и HTTPS. Эти решения не блокируют проектирование БД и реализацию приложения. Эта подготовка репозитория не создает инфраструктуру и не запускает деплой.

## 10. Решения до начала реализации

Принятым контрактом закрыты вопросы границ дня и принадлежности ночи, ночных разрывов и быстрых отметок, одной заметки на фактический/текущий интервал, отсутствия заметок у прогноза. Подтверждение email и восстановление пароля не входят в минимальный API первой версии. Новый frontend использует JavaScript согласно выбранному стеку.

Остается:

1. Проектирование схемы БД (P-05) завершено в `api/DATABASE.md`; числовые примеры прогноза (P-03) утверждены. Основа FastAPI и PostgreSQL с миграциями (B-01/B-02) реализованы; основа репозиториев и Unit of Work (B-03) реализована. Расширенные тесты хранения (T-01c) выполнены; основа React/Vite (F-01) реализована. Все бизнес-этапы и локальный запуск выполнены. Осталась настройка внешнего окружения по I-01a/I-04.
2. Размещение `dev` и `prod` на одном VPS и схема доменов утверждены: основной домен — prod, поддомен `dev` — разработка, API — `/api/v1` на соответствующем origin. Порядок выпуска утвержден: ручной деплой PR в dev после проверок, автоматический деплой main в dev и ручное продвижение проверенных образов в prod. Доставка по SSH из GitHub Actions с GHCR утверждена; используются repository secrets и отдельные workflow, совместимые с GitHub Free. Выбор конкретного VPS/провайдера и доменного имени отложен до настройки доставки (I-01a) и не блокирует реализацию приложения. Резервное копирование, сроки хранения копий и цели восстановления исключены из прототипа.

Перенос данных старого калькулятора отклонен: импорт из `localStorage` и миграционный экспорт не входят в задачи проекта.

## 11. Критерии готовности первой версии

- Все обязательные возможности раздела 1 реализованы; пользовательские данные сохраняются между днями и устройствами.
- Факты, текущие длительности и прогноз визуально и численно разделены.
- Изменения графиков не переписывают историю, комментарии не теряются при пересчете.
- Проверки API подтверждают изоляцию пользователей, ограничения admin и немедленное прекращение доступа после блокировки.
- Миграции, развертывание и возврат предыдущего релиза приложения проверены; dev и prod изолированы. Восстановление БД из резервной копии не входит в критерии готовности прототипа.
- Документация позволяет запустить приложение, вручную создать admin и выпустить проверенный релиз.
