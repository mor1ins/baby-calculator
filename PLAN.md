# План переработки калькулятора сна и бодрствования

Статус: подготовка репозитория и проектирование. Бизнес-код, миграции, Docker-контейнеры и деплой пока не реализованы. Подключены технический каркас backend (DI и шина), линтеры, архитектурные тесты и GitHub Actions для проверок; правила — в `backend/AGENTS.md`, описание — в `backend/README.md`.

## 1. Цель и границы

Перейти от однодневного калькулятора в браузере к многопользовательскому дневнику с постоянным хранением истории, персональными графиками и прогнозом текущего дня.

Обязательные возможности первой версии:

- Самостоятельная регистрация, вход и выход; роли `user` и `admin` с возможностью расширения.
- Хранение данных пользователя за произвольное число дней в PostgreSQL.
- Ввод только фактических интервалов сна; вычисление бодрствования между ними.
- Комментарии к интервалам сна и вычисленным интервалам бодрствования.
- Несколько персональных графиков и выбор графика для конкретного дня.
- Главная страница: текущий день, факты, текущий интервал, прогноз и метрики.
- Метрики дневного сна, ночного сна и дневного бодрствования.
- Администратор видит всех пользователей и их сохраненные данные, но не редактирует дневники, графики и комментарии. Отдельное разрешенное действие — блокировка учетной записи.
- Учетная запись администратора создается вручную в БД, без публичной регистрации администратора.
- Контейнерное развертывание через GitHub Actions, отдельные окружения `dev` и `prod`.

Утвержденные ограничения первой версии (подтверждены пользователем 3 октября 2026 года):

- Один дневник ребенка на пользователя.
- Русский интерфейс.
- Без совместного доступа родителей.
- Без уведомлений.
- Без медицинских рекомендаций.

## 2. Репозиторий

```text
.
├── PLAN.md
├── .gitignore
├── only_web_version/     # Вся прежняя версия, включая ее конфигурацию и workflow
├── frontend/             # Будущий React-клиент
├── backend/              # Будущий FastAPI-сервис и миграции
├── deploy/               # Будущие Dockerfile, Compose, proxy и инструкции эксплуатации
└── tests/                # Будущие интеграционные и сквозные тесты, общие фикстуры
```

Каталоги `deploy` и корневой `tests` содержат `.gitkeep`, чтобы Git сохранял их. В `backend` добавлены технический каркас, настройки и тесты. В `frontend` подключены линтеры, проверки границ слоев и дублирования, архитектурные тесты и CI; runtime приложения пока отсутствует. Метаданные `.git` оставлены в корне. В корне создан новый `.gitignore`; прежний сохранен в архиве без изменений. Локальные `node_modules`, `dist` и файлы сборки тоже перенесены и остаются игнорируемыми.

Старая версия запускается из `only_web_version`: `npm ci`, затем `npm run dev`. Ее исходный `base` для GitHub Pages сохранен. Перенесенный `only_web_version/.github/workflows/deploy.yml` больше не является активным workflow GitHub Actions. Уже опубликованный сайт этим переносом не удаляется. Будущие workflow новой версии должны находиться в корневом `.github/workflows/`, а не в `deploy/`.

В старой версии данные находятся в `localStorage` браузера. Перенос исходников не переносит эти данные в новую БД; возможность импорта рассматривается отдельно.

## 3. Предлагаемая архитектура и стек

Один backend с модулями авторизации, пользователей, дневника, графиков, расчетов и администрирования. Frontend обращается к REST API `/api/v1`. Расчеты на backend являются единым источником результата; frontend отображает их и обновляет текущие счетчики.

| Область | Решение | Назначение |
| --- | --- | --- |
| Backend | Python, FastAPI, Uvicorn, Pydantic | HTTP API, валидация, OpenAPI |
| Данные | PostgreSQL, SQLAlchemy, psycopg, Alembic | Хранение, транзакции и версионируемые миграции |
| Frontend | React, JavaScript, Vite | SPA; TypeScript можно согласовать отдельно, он уже есть в архиве |
| Работа с API | TanStack Query, React Router | Серверное состояние, маршрутизация |
| Формы | React Hook Form | Ввод сна, графиков и учетных данных |
| Авторизация | Серверные сессии в PostgreSQL, HttpOnly cookie | Отзыв доступа при выходе и блокировке |
| Пароли | Argon2id через поддерживаемую библиотеку | Хранение только хешей |
| Проверки | pytest, HTTPX; Vitest, Testing Library; Playwright | Расчеты, API, компоненты, пользовательские сценарии |
| Качество | isort, flake8, mypy, pylint, import-linter; ESLint, Prettier, Stylelint, dependency-cruiser, jscpd | Стиль образца, типизация, дублирование и изоляция слоев |
| Доставка | Docker, Docker Compose, GitHub Actions, GHCR | Сборка и публикация образов, развертывание |
| Входящий трафик | Nginx и HTTPS | Статика frontend и проксирование `/api` |

Версии зависимостей и базовых образов выбираются и фиксируются при инициализации новой версии. Для Python — `pyproject.toml` и lock-файл uv; для frontend — npm и `package-lock.json`. Redis и очередь задач пока не требуются.

FastAPI допускает выбор ORM; SQLAlchemy здесь — проектное предложение ([документация FastAPI](https://fastapi.tiangolo.com/tutorial/sql-databases/)). Для `dev` и `prod` планируются GitHub Environments с отдельными секретами и правилами развертывания; доступность конкретных защит зависит от тарифа и видимости репозитория ([документация GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)).

Backend разделен на `api`, `application`, `domain`, `infrastructure`; взаимодействие слоев — через контракты и `mediapyr`, зависимости собираются в `dependency-injector`. Для доступа к БД утвержден паттерн «Репозиторий»: интерфейсы в `contracts`, реализации в `infrastructure/repositories`, инъекция в persistence-обработчики через контейнер. Остальные слои обращаются к данным через шину. Атомарность обеспечивает инжектируемый Unit of Work с общей сессией и централизованным commit/rollback. Конкретные правила, запреты импортов и бюджет переходов закреплены в `backend/AGENTS.md`.

## 4. Правила предметной области

Следующие правила — предлагаемый контракт для реализации. Пограничные случаи необходимо согласовать до написания расчетов.

### 4.1. Время, день и история

- Хранить начало и конец сна как абсолютные моменты времени (`timestamptz`), часовой пояс дневника — идентификатор IANA, например `Europe/Moscow`.
- В интерфейсе вводить дату и время, чтобы сон через полночь не требовал догадок.
- Предлагаем считать днем дневника цикл от окончательного утреннего пробуждения до следующего окончательного утреннего пробуждения. Дата дня — локальная дата начала цикла; ночной сон относится к дню, после которого он начался.
- Вчерашний ночной сон показывать утром как контекст, не прибавляя его повторно к метрикам сегодняшнего цикла.
- Окончательное утреннее пробуждение определяется завершением последнего отрезка ночного сна с признаком завершения ночи. Это уточнение записи сна, а не ручной ввод бодрствования.
- Ночные пробуждения задаются разрывами между отрезками ночного сна одной ночи. Эти разрывы не входят в дневное бодрствование.
- Если граница дня неизвестна, показывать неполноту данных, а не считать отсутствие записей подтвержденным бодрствованием. Для первого дня достаточно внести предшествующий ночной сон и его окончание.
- Длительности считать по абсолютному времени, включая смену часового пояса и переходы летнего времени. Часовой пояс прошедшего дня сохранять, чтобы смена настроек не перемещала историю.

### 4.2. Фактические интервалы и комментарии

- Сон: начало, конец (может отсутствовать у текущего сна), тип `дневной` / `ночной`, комментарий.
- Пользователь может добавлять, исправлять и удалять собственные записи, в том числе за прошлые дни.
- Не более одного незавершенного сна на дневник; пересечения запрещены, конец строго позже начала. Проверять конфликты и при одновременных запросах.
- Реальные будущие интервалы не создавать: будущее принадлежит прогнозу. Соседние интервалы могут касаться границами; нулевое бодрствование не показывается.
- Бодрствование вычисляется как промежуток между окончанием одного сна и началом следующего; текущий промежуток — до текущего времени. Ночные разрывы отмечаются отдельно.
- Комментарии к вычисляемому бодрствованию хранить отдельно, с привязкой к ID соседних снов, а не к порядковому номеру на экране. Для текущего бодрствования допускается незаполненная правая граница; при появлении следующего сна она закрепляется.
- После исправления времени соседних снов комментарий сохраняется. Если удаление или вставка сна разрушает промежуток, комментарий сохраняется как требующий перепривязки; пользователь решает, к чему его привязать. Молчаливое удаление недопустимо.
- Для прогнозных интервалов комментарии в первой версии не предполагаются: они еще не являются записями дневника. Это ограничение нужно согласовать.

### 4.3. Графики

График — именованный шаблон последовательности длительностей. У пользователя может быть несколько шаблонов, например «Обычный день» и «Во время болезни». Графики доступны в отдельном разделе и через переключатель на странице дня.

Пример пользовательского графика:

| Интервал | Длительность |
| --- | --- |
| Бодрствование 1 | 4:20 |
| Дневной сон 1 | 1:20 |
| Бодрствование 2 | 4:40 |
| Дневной сон 2 | 0:20 |
| Бодрствование 3 | 3:00 |
| Ночной сон | 10:00 |

В примере дневной сон — **1:40**, дневное бодрствование — **12:00**, ночной сон — **10:00**, весь цикл — **23:40**. Не дополнять автоматически до 24 часов: показывать сумму и отклонение, разрешать сохранить такой график.

- Длительности — положительное целое число минут; отображение `ч:мм`.
- Последовательность: бодрствование и дневной сон чередуются, последнее дневное бодрствование завершается ночным сном. Допускается день без дневных снов.
- Шаблоны можно создавать, переименовывать, копировать, изменять и архивировать; один можно назначить по умолчанию.
- Для дня сохраняется снимок выбранного графика. Изменение или архивирование шаблона не меняет историю.
- Замена графика конкретного дня меняет только его план и прогноз, сохраняя фактические записи. Пока график не выбран, факты и метрики доступны, прогноз отсутствует.

### 4.4. Метрики и прогноз

- Дневной сон: сумма фактических длительностей дневных снов выбранного цикла.
- Ночной сон: сумма отрезков ночного сна, относящихся к этому циклу, без ночных пробуждений.
- Дневное бодрствование: сумма промежутков от утреннего пробуждения до начала ночи за вычетом дневных снов; ночные пробуждения исключаются.
- Для текущего интервала показывать прошедшую длительность отдельно от завершенных интервалов; итог «на сейчас» может включать ее с явной отметкой. Прогноз не входит в фактические метрики.
- API возвращает признак полноты данных: неизвестное значение не подменяется нулем.
- Прогноз строится от фактического утреннего пробуждения, затем корректируется после каждого фактического сна по последовательности выбранного графика.
- Дневные сны сопоставляются с планом по порядку; завершенные интервалы всегда остаются фактическими. Будущие длительности берутся из снимка графика.
- Для текущего интервала ожидаемый конец = его фактическое начало + плановая длительность. Если это время уже прошло, показывать превышение; дальнейшую временную линию считать от текущего времени и помечать условной до фактического окончания интервала.
- Показывать ближайшее укладывание/пробуждение, предполагаемое начало ночи и следующий утренний подъем.
- При лишнем дневном сне после исчерпания плана применять последнее плановое дневное бодрствование и показывать расхождение. При пропущенном сне не угадывать намерение: пользователь выбирает другой график либо фиксирует начало ночи, которое завершает дневной прогноз.
- Пересчитывать после добавления, изменения, удаления сна, смены графика и обновления текущего времени. Для прошлых завершенных дней отображать факты и сохраненный план.

## 5. Пользователи и права

| Действие | user | admin |
| --- | --- | --- |
| Просмотр своего дневника и графиков | Да | Если есть собственный дневник и право пользователя |
| Изменение своего дневника и графиков | Да | Только при отдельном праве пользователя |
| Просмотр всех пользователей и их данных | Нет | Да, только чтение |
| Изменение чужих снов, графиков и комментариев | Нет | Нет |
| Блокировка/разблокировка обычного пользователя | Нет | Да, разблокировка предложена для первой версии |
| Назначение ролей через публичный API | Нет | Нет в первой версии |

- Роли хранить в таблицах `roles` и `user_roles`; проверки строить вокруг разрешений, с запретом по умолчанию. Новая роль не должна требовать изменения enum в БД.
- Регистрация всегда назначает только `user`, поля роли и блокировки не принимаются от клиента.
- Проверять владельца объекта на backend при каждом доступе, включая вложенные ресурсы и выбор чужого шаблона.
- У администратора отдельные маршруты чтения и отдельное действие смены статуса пользователя; универсального административного редактирования данных нет.
- Блокировка запрещает вход и доступ к API, отзывает активные сессии, сохраняет дневник. Предложение: запретить блокировку администраторов и самого себя через интерфейс.
- Сессии: случайный непрозрачный токен, в БД его хеш, срок действия и отзыв. Cookie `HttpOnly`, `Secure`, `SameSite`; CSRF-защита изменяющих запросов. Пароли и токены исключить из логов и API-ответов.
- Ограничить частоту попыток входа и регистрации; возвращать понятные ошибки без раскрытия чужих данных.
- Подготовить инструкцию ручного создания admin: генерация хеша штатной библиотекой, транзакционная вставка пользователя и роли в БД, проверка входа. Без фиксированного пароля в миграциях, автоматического admin seed и endpoint создания admin.
- Журналировать блокировки/разблокировки с исполнителем, временем и причиной.

## 6. Предварительная модель данных

| Сущность | Основное содержимое |
| --- | --- |
| `users` | ID, нормализованный уникальный email, хеш пароля, статус, даты создания и блокировки |
| `roles`, `user_roles` | Коды ролей и назначения пользователям |
| `sessions` | Пользователь, хеш токена, срок действия, отзыв |
| `diaries` | Владелец и часовой пояс; в первой версии один дневник на пользователя |
| `schedule_templates` | Владелец, название, признак архивирования/выбора по умолчанию |
| `schedule_segments` | Шаблон, порядок, тип, длительность в минутах |
| `diary_days` | Дневник, дата, часовой пояс, границы цикла, признак полноты, снимок графика |
| `sleep_intervals` | Дневник/цикл, тип сна, начало, конец, завершение ночи |
| `interval_comments` | Текст, автор, ссылка на сон либо соседние сны бодрствования, состояние перепривязки |
| `admin_audit_log` | Исполнитель, действие, целевой пользователь, причина, время |

Ограничения: уникальность дня в дневнике, внешние ключи, проверка длительностей, единственный открытый сон, отсутствие пересечений внутри дневника. Индексы — по владельцу, дневнику/времени сна и дате дня. Метрики и будущие интервалы не хранить как факты: вычислять из записей и снимка графика. Исправления границ сна должны транзакционно обновлять принадлежность к циклам и связи комментариев.

## 7. Интерфейс и API

Основные экраны: регистрация/вход; «Сегодня»; история с выбором даты; «Мои графики» с редактором; настройки часового пояса; список пользователей администратора; просмотр выбранного дневника администратором без кнопок изменения.

Главный экран адаптировать для телефона: переключатель даты и графика, три метрики, временная линия с различимыми фактом/текущим состоянием/прогнозом, добавление и завершение сна, комментарии. Предусмотреть состояния загрузки, отсутствия данных, неполной истории, ошибок и блокировки учетной записи.

Группы API (точные схемы закрепить в OpenAPI до интеграции):

- `/api/v1/auth`: регистрация, вход, выход, текущая сессия.
- `/api/v1/me`: профиль и настройки дневника.
- `/api/v1/schedules`: собственные шаблоны и их интервалы.
- `/api/v1/days/{date}`: снимок графика, временная линия, метрики, прогноз.
- `/api/v1/sleeps`: создание, изменение, завершение и удаление сна.
- `/api/v1/comments`: комментарии и перепривязка к интервалам.
- `/api/v1/admin/users`: список, карточка, чтение дневника и графиков, отдельные действия блокировки/разблокировки.

Списки пользователей и истории — с пагинацией. Ошибки имеют единый формат; конкурентное изменение записи обнаруживается по версии. Административные ответы не содержат хешей паролей, токенов и секретов.

## 8. Окружения и доставка

- Локальная разработка: Compose для PostgreSQL и приложения; отдельные команды установки зависимостей, миграций и тестов.
- `dev` и `prod`: отдельные БД, volumes, учетные данные, домены и GitHub Environments. Данные prod не копировать в dev без отдельной процедуры обезличивания.
- Предлагаемый процесс: pull request → проверки; merge в `main` → сборка образов и автоматический deploy в dev; выбранный проверенный commit/release → deploy в prod.
- Собирать образы frontend/backend один раз, отмечать SHA коммита и продвигать те же digest из dev в prod. Не использовать `latest` как единственный идентификатор релиза.
- Секреты — в GitHub Environments/на сервере, примеры конфигурации без значений — в `.env.example`. БД не публиковать в интернет.
- Миграции запускать отдельным шагом до приложения, исключить параллельные миграции. Перед опасными изменениями — резервная копия; предпочитать совместимые миграции.
- После деплоя проверять readiness API, доступность БД и основной сценарий. При неуспехе — остановка продвижения и возврат предыдущего образа; откат схемы БД планируется отдельно и не подразумевается автоматически.
- Настроить резервные копии PostgreSQL, срок хранения и проверку восстановления. Подготовить логи, healthchecks, ротацию и минимальные оповещения о недоступности.
- Конкретный сервер/провайдер, домены и механизм доставки на сервер выбираются отдельно. Эта подготовка репозитория не создает инфраструктуру и не запускает деплой.

## 10. Решения до начала реализации

Эти вопросы не блокируют текущий перенос файлов, но должны быть закрыты на этапе 1:

1. Подтвердить цикл от утреннего пробуждения до следующего утра и отнесение ночи к предшествующему дню. Альтернатива — календарный день или учет ночи по дате пробуждения.
2. Подтвердить учет ночных пробуждений отдельными отрезками сна и признак окончательного завершения ночи.
3. Нужны ли комментарии к будущим плановым интервалам, несколько комментариев на интервал или достаточно одной редактируемой заметки?
4. Подтвердить JavaScript или выбрать TypeScript для нового frontend.
5. Нужны ли подтверждение email и восстановление пароля в первом выпуске; если да, выбрать почтовый сервис и добавить задачи токенов, писем и тестов.
6. Выбрать инфраструктуру, домены, правила выпуска prod, сроки хранения резервных копий и целевое время восстановления.
7. Нужен ли импорт имеющегося `localStorage`; если да, добавить отдельный экспорт/импорт с проверкой формата, часового пояса и защитой от дублей.
