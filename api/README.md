# Контракт frontend ↔ backend, v1

Источник истины — **[openapi.yaml](openapi.yaml)**, OpenAPI 3.1.1. Все 23 операции контракта реализованы в backend; интеграционные тесты проверяют ответы по этим схемам. Дизайн первой версии принят; остается в `design/`, контракт — в `api/`.

Схема хранения и транзакций — в [DATABASE.md](DATABASE.md); миграции и репозитории находятся в backend.

Один пользователь — один дневник. HTTP JSON, префикс `/api/v1`, cookie-сессия. Главный экран получает день целиком одним запросом. Внутренние контейнеры, слои, шина и репозитории не являются частью публичного API.

## 1. Минимальная поверхность

В таблице пути указаны без `/api/v1`.

| Назначение | Методы и пути |
| --- | --- |
| Авторизация | `GET /session`, `POST /session`, `DELETE /session`, `POST /register` |
| Настройки | `PATCH /me` |
| День и история | `GET /days?from=…&to=…`, `GET /days/{date}` |
| График конкретного дня | `PUT /days/{date}/schedule` |
| Записи сна | `POST /sleeps`, `PATCH /sleeps/{sleep_id}`, `DELETE /sleeps/{sleep_id}` |
| Ночные отметки | `PUT /sleeps/{sleep_id}/events/{event_id}`, `DELETE` по тому же пути |
| Шаблоны графиков | `GET /schedules`, `POST /schedules`, `PATCH /schedules/{schedule_id}` |
| Заметки | `PUT /comments/{comment_id}`, `DELETE /comments/{comment_id}` |
| Admin: пользователи | `GET /admin/users`, `PATCH /admin/users/{user_id}/status` |
| Admin: чтение | `GET /admin/users/{user_id}/days`, `GET /admin/users/{user_id}/days/{date}`, `GET /admin/users/{user_id}/schedules` |

Всего **23 операции на 17 путях**. Нужные для чтения отдельного сна, его событий и заметок данные уже входят в ответ дня. Нет отдельных API метрик/прогноза, ручного бодрствования, копирования шаблона, переключения ролей, регистрации администратора, WebSocket и универсального редактирования чужих данных.

## 2. Общие правила

- Имена JSON-полей — `snake_case`. ID ресурсов — UUID, кроме непрозрачных ID вычисленных интервалов. Клиент не разбирает и не конструирует ID интервала.
- Дата дня — `YYYY-MM-DD` в часовом поясе дневника. Моменты времени — RFC 3339 с часовым поясом; ответы backend — UTC с `Z`. На экране frontend показывает локальное время `Day.timezone`.
- Длительности шаблонов — целые **минуты**. Фактические длительности/метрики — целые **секунды**: backend суммирует точное время и округляет вниз только итог до секунды. Frontend форматирует для показа в часах/минутах, не пересчитывает прогноз и границы бодрствования.
- `null` означает неизвестное/отсутствующее значение. `0` — известный нулевой итог. Не подменять одно другим.
- PATCH изменяет только переданные поля. `null` явно очищает только nullable-поле. Пустой PATCH и неизвестные поля — `422`. Для очистки текста заметки используется DELETE.
- Изменения одной операции атомарны. Ответ отдается после сохранения. Отдельные HTTP-запросы не являются общей транзакцией.
- История запрашивается включительным диапазоном максимум 31 день, только существующие дни, `date DESC`. Пагинация календаря — соседними диапазонами. Список шаблонов небольшой, без пагинации, включая архивные. Список пользователей — курсор, `limit` по умолчанию 30, максимум 100.

### Версии и конфликты

Изменяемые ресурсы содержат целочисленный `version`. Для PATCH/DELETE сна, PATCH профиля/шаблона/статуса, PUT/DELETE заметки и PUT графика дня нужен `If-Match: "<version>"`.

Версия заметки берется из `Comment`, сна — из `Sleep`, пользователя — из `User`, шаблона — из `Schedule`; назначение графика использует `Day.version`. Для создания заметки и изменения пустого дня — `If-Match: "0"`. Заметки получают UUID на клиенте. Версия нового сохраненного ресурса — 1; изменение увеличивает ее.

`412 version_conflict` означает, что данные изменились: перечитать ресурс через его экран/список, сохранить введенный текст в форме, предложить сверить изменения. Не повторять запись поверх новой версии автоматически. Без заголовка — `428 version_required`. Это проверка версии сохраненного состояния, а не кеширование изменяющегося по часам ответа дня.

Любое изменение снов, заметок, событий или снимка плана увеличивает версии затронутых дней. Изменение события или заметки сна также увеличивает `Sleep.version`. Изменение вычисленных границ/привязки заметки увеличивает ее версию. Течение времени само по себе версии не меняет. Добавление события не требует If-Match и сериализуется с завершением/исправлением сна в БД.

После записи frontend инвалидирует кеш дней/истории и перечитывает открытый день: исправление сна может затронуть соседние даты. После изменения шаблона обновляет список; после архивирования также обновляет `/session`, поскольку может сброситься график по умолчанию.

## 3. Авторизация

1. При запуске запросить `GET /session` с cookie. До входа ответ содержит `user: null` и `csrf_token`, backend создает анонимную cookie-сессию.
2. На **все** изменяющие запросы, включая вход/регистрацию/выход, передавать эту cookie и `X-CSRF-Token`. Токен привязан к сессии; сервер также проверяет Origin для запросов браузера.
3. Регистрация и вход возвращают `Session`, ротируют идентификатор сессии и CSRF-токен. Токен хранится в памяти frontend, пароль после отправки очищается.
4. Cookie `session`: `HttpOnly; Secure; SameSite=Lax; Path=/`, без Domain. Frontend и API работают с одного origin. `GET /session` и ответы с персональными данными имеют `Cache-Control: no-store`.
5. Выход отзывает сессию и очищает cookie. `/session` заново выдает анонимный контекст при следующем запуске. Logout разрешен и для анонимного/заблокированного контекста с валидным CSRF.

Регистрация принимает только имя, email, пароль и часовой пояс; назначается роль `user`. Роли в ответе — массив строк, не закрытый enum. Пользовательские операции требуют `user` и работают только с собственным дневником; административные — `admin`. Наличие admin не разрешает чужие записи и не дает автоматически права user.

Блокировка немедленно отзывает все сессии. Известная заблокированная сессия/попытка входа получает `403 account_blocked`; истекшая или неизвестная сессия — `401 unauthenticated`. После разблокировки нужен новый вход. Создание admin и назначение ролей остаются ручными операциями в БД.

## 4. Один ответ для экрана дня

`GET /days/2026-10-03` возвращает:

- `date`, `timezone`, `as_of`, `version`, `complete`;
- сохраненный `schedule` или `null`;
- `previous_night`: последний отрезок предшествующей ночи, задающий утреннюю границу, либо `null`;
- `sleeps`: реальные записи **этого** цикла с версиями и массивами ночных событий;
- `timeline`: готовая отсортированная временная линия со статусами `actual`, `ongoing`, `forecast`, ссылками на реальные сны и заметками;
- `metrics`: дневной сон, ночной сон, дневное бодрствование на `as_of`;
- `orphaned_comments`: сохраненные заметки, утратившие интервал;
- `issues`: машинные признаки неполноты/расхождения с планом.

`previous_night` не прибавляется к метрикам этого цикла. Он нужен для контекста и редактирования утренней границы. Для изменения заметки самой предыдущей ночи открыть ее `day`.

У факта `end` задан. У текущего интервала `end=null`, `duration_seconds` — прошедшее время, `expected_end` — ожидаемый конец либо null. Прогнозный интервал имеет `id=null`, `sleep_id=null`, `comment=null`: его нельзя редактировать как факт. Заметка сохраняется по `timeline[].id`; `sleep_id` связывает строку с редактируемым объектом `sleeps`.

Прогноз следует очередности интервалов сохраненного графика, опирается на фактические границы, не переписывает прошлое и не дополняет цикл до 24 часов. При превышении плана возвращается `plan_exceeded`; дальнейший прогноз начинается не раньше `as_of`. У текущего периода `expected_end` может сохранять уже прошедший плановый ориентир, UI показывает превышение, а не отрицательный таймер. Следующее событие UI берет из текущего `expected_end` и будущих интервалов, отдельный endpoint не нужен.

Без графика — факты и метрики, без прогноза. Без утренней границы — `missing_morning`, неизвестное дневное бодрствование `null`, без выдуманного прогноза. Отсутствующая дата возвращает пустой Day с `version=0`, не 404; GET не создает запись. Активный экран перечитывает день примерно раз в минуту и при возвращении вкладки в фокус. Backend — источник расчетов.

В принятом контракте v1 используем модель из плана: цикл от окончательного утреннего подъема до следующего; ночь относится к предшествующему дню. В `SleepWrite.day` дата цикла задается явно. Заданный `end` ночного сна автоматически задает следующее утро. Отдельная пользовательская метка не требуется; устаревшее входное поле `ends_night` принимается для совместимости, но сервер вычисляет его сам. Его локальная дата окончания начинает следующий цикл. Backend проверяет соответствие дат/времени и границ цикла, не угадывает это по одному времени суток. Завершенным считается цикл с известными обеими утренними границами и без открытых снов; иначе `complete=false`. Эти правила приняты вместе с контрактом; статусы задач отражены в PLAN.md.

## 5. Основные сценарии записи

### «Уснул», «Проснулся», исправление

- Начать: `POST /sleeps` с `day`, `kind`, `start`, `end:null`.
- Завершить дневной сон: `PATCH /sleeps/{id}` с `end` и If-Match из Sleep.
- Короткое ночное пробуждение без измерения времени: событие, как описано ниже; сон не закрывать.
- Окончательный утренний подъем: PATCH ночного сна с `end`. Краткие пробуждения внутри ночи записываются ночными отметками и не завершают сон.
- Первый день: записать предшествующую ночь с `day` предыдущего дня, ее концом утром; затем перечитать текущий день.
- Исправить: PATCH только измененных полей. Один открытый сон на дневник, никакого пересечения, `end > start`, опережение серверного времени меньше настроенного допуска (по умолчанию 20 минут). Для дневного сна сервер всегда устанавливает `ends_night=false`. Проверяется итоговое состояние после PATCH.
- Удалить ошибочный сон: DELETE с If-Match; зависимые заметки не теряются. Если есть ночные отметки, сервер просит сначала явно удалить их.

Смена границ пересчитывает все затронутые дни. Если изменение разрушает вычисленный интервал бодрствования, его заметка оказывается в `orphaned_comments` исходного дня. Обычное исправление времени с теми же соседними снами сохраняет ID интервала/заметку. Текущий промежуток сохраняет ID при появлении следующего сна.

### Заметка

Одна заметка на фактический/текущий интервал. Создать: клиент генерирует UUID и выполняет `PUT /comments/{id}` с `If-Match: "0"`, `target_id` из timeline и `text`. Исправить или перепривязать: тот же URL, текущая версия, новый текст/target_id. Удалить: DELETE. Вторую заметку на занятый интервал сервер отклоняет.

Если форма одновременно изменяет сон и его заметку, клиент сначала сохраняет сон, перечитывает день и сохраняет заметку с актуальной версией. Это две отдельные записи: при ошибке второй показать, что сон сохранен, а заметка еще нет; не очищать текст и не повторять создание сна.

### Ночная отметка одним нажатием

Клиент один раз создает `event_id` и фиксирует `occurred_at`, выполняет PUT. Повтор после сетевого сбоя отправляет **тот же** URL и тело: 201 при создании, 200 при идентичном повторе. Событие в ответе Sleep неизменно. Другой payload под тем же ID — 409. Новая отметка разрешена только внутри текущего ночного сна с опережением серверного времени меньше настроенного допуска; существующий идентичный запрос допускается повторить после завершения сна.

Число отметок — `sleep.events.length`, журнал — этот же массив. Для отмены передается конкретный ID, а не команда «уменьшить счетчик». DELETE можно повторить. Удаленный ID хранится как использованный и не воскресает от запоздавшего PUT (`event_deleted`). События привязаны к одному сну; если ночь записана несколькими отрезками, общий журнал ночи — объединение событий ее отрезков.

При завершении/исправлении сна события сохраняются. Если новые границы исключают отметку, `409 events_outside_sleep`, изменение целиком отклоняется. Длительность эпизода неизвестна: события не меняют время сна, бодрствование и прогноз.

### Графики

POST создает шаблон; копирование использует тот же POST. PATCH меняет имя/описание/segments или `archived`. Последовательность — `awake, (nap, awake)*, night`; допускается отсутствие дневных снов. Длительности положительные, сумма может быть 23:40 или другой.

`PATCH /me` назначает `default_schedule_id`. Пока график дня не инициализирован, GET дня возвращает актуальный график по умолчанию без записи в БД — в том числе до первого сна и после утреннего подъёма. При первом создании дня записью сна копируется действующий график по умолчанию; без него snapshot=null. `PUT /days/{date}/schedule` явно заменяет снимок дня, включая повторное применение обновленного шаблона; `schedule_id:null` убирает план только с этой даты. Старые факты сохраняются. Архивирование не удаляет снимки; архивный шаблон нельзя назначить снова до разархивирования.


При сохранении отредактированного шаблона доступны два утвержденных режима:

- **«Начиная с сегодняшнего дня»**: PATCH шаблона с его If-Match, затем PUT `/days/{today}/schedule` с ID шаблона и If-Match сегодняшнего дня. Сегодня определяется в часовом поясе дневника. Перед подтверждением UI показывает, какой график будет заменен сегодня, если сейчас выбран другой.
- **«Для следующих дней»**: только PATCH шаблона; сегодняшний снимок остается прежним.

Оба режима сохраняют снимки прошлых и уже назначенных будущих дней. Новые дни получают обновленный шаблон, когда он является default или назначается явно; default сам по себе не меняется. Изменения плана не меняют факты сна, прогноз пересчитывается после перечитывания дня.

Это два отдельных запроса, общей транзакции нет. Если шаблон сохранен, а назначение на сегодня не удалось, UI сообщает «График сохранен, но не применен к сегодняшнему дню» и позволяет повторить только применение. При конфликте версии дня перечитать его и предложить сверить новый выбор, не перезаписывать автоматически. Запрос применения копирует актуальную версию шаблона на момент PUT; интерфейс показывает полученный снимок. Новый endpoint и параметр даты начала действия шаблона не требуются.

## 6. Ошибки и доступ

Единый ответ: `{ "code": "sleep_overlap", "message": "…", "fields": { "start": "…" } }`. `fields={}`, если ошибка не привязана к полям. Клиент ветвится по code, неизвестные коды показывает через message. Стандартные ошибки валидации FastAPI преобразуются в этот формат.

| HTTP | Коды / смысл |
| --- | --- |
| 401 | `unauthenticated`, `invalid_credentials` |
| 403 | `forbidden`, `account_blocked`, `csrf_invalid` |
| 404 | `not_found`: ресурс отсутствует или не принадлежит пользователю |
| 409 | `sleep_overlap`, `open_sleep_exists`, `events_outside_sleep`, `sleep_has_events`, `sleep_closed`, `idempotency_conflict`, `event_deleted`, `comment_target_changed`, `comment_exists`, `email_taken`, `schedule_archived` |
| 412 | `version_conflict` |
| 422 | `validation_error`: формат, превышение допуска опережения времени, порядок времен/графика, timezone, диапазон истории |
| 428 | `version_required` |
| 429 | `rate_limited`, с заголовком `Retry-After` в секундах |
| 500 / 503 | `internal_error` / `unavailable`, без stack trace и секретов |

Admin видит все данные, включая архивные шаблоны, заметки и ночные события заблокированных пользователей. Единственная административная запись — `/status`, только blocked и причина. Самоблокировка, блокировка admin, смена ролей и изменение чужого дневника запрещены. Причина идет в аудит, журнал аудита отдельным API в v1 не публикуется.

## 7. Примеры и проверка

Утвержденные сценарии расчета прогноза — в [FORECAST_EXAMPLES.md](FORECAST_EXAMPLES.md). Они покрыты тестами сервиса расчета (T-05).

В `examples/`: полный день в 14:20 (Москва), пустой день, сессия, текущий ночной сон с отметкой, ошибка, создание сна и добавление события. В примере: дневной сон 4800 секунд (1:20), дневное бодрствование 23400 (6:30), ночь еще не началась — null.

```sh
python3 -m venv /tmp/baby-api-check
/tmp/baby-api-check/bin/pip install -r api/requirements-dev.txt
/tmp/baby-api-check/bin/python api/validate.py
```

Проверяются структура OpenAPI, JSON-примеры, запрет лишних полей/самоназначения роли, ручного бодрствования, даты без часового пояса и заметки у прогноза. Это проверка контракта; транзакции, права, идемпотентность и расчеты необходимо проверить интеграционными тестами после реализации.

Контракт основан на [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html). Подтверждение email, восстановление пароля, уведомления и совместные дневники не добавлены в минимальный API; их реализация требует отдельного изменения контракта.

Публичная регистрация управляется серверным `BABY_REGISTRATION_ENABLED`
(по умолчанию `false`). При выключенном флаге валидный `POST /register`
возвращает `403 registration_disabled` до обращения к хранилищу.
Вход и существующие сессии остаются доступны.


## 8. Профиль малыша, укладывание и статистика

Миграция `0005_design_features` добавляет профиль малыша и его отдельную версию,
обстоятельства дня, укладывания, изменения режима, публичные снимки и описание графика.
Существующие пользователи, графики и записи сна сохраняются.

- `GET/PUT /child`: частные сведения о малыше; PUT заменяет профиль целиком с If-Match.
  Фото предварительно уменьшается в браузере до 512 px; сервер принимает только data URL
  JPEG/PNG/WebP до 400000 символов. Дата рождения не может быть в будущем.
- `POST /settling`: начать укладывание сегодня. Одновременно разрешено только одно
  укладывание, несовместимое с открытым сном. PATCH завершает попытку без сна,
  DELETE отменяет её. Обе операции требуют версию. Создание открытого сна атомарно
  связывает укладывание с засыпанием; неверное время откатывает всю запись.
  Правка начала сна меняет окончание укладывания; удаление сна оставляет попытку без сна.
- `PUT /days/{date}/context`: обстоятельства и личная заметка с версией дня.
  `POST /changes`, `DELETE /changes/{id}`: отметки изменений режима.
- `GET /statistics?from=...&to=...`: 1–366 календарных дней включительно, не позже сегодня.
  Средние сна и бодрствования используют только полные циклы. Неполный цикл не превращается
  в нулевую ночь. Укладывание входит в бодрствование, а не увеличивает общую длительность дня.
- `POST /shares`: неизменяемый снимок выбранного периода. Ответ содержит случайный токен
  один раз; в БД хранится его хеш. `GET /shares` возвращает метаданные, DELETE отзывает ссылку.
  `GET /public/reports/{token}` доступен без входа. Публикуются имя/возраст/фото малыша,
  интервалы, отметки изменений и краткие обстоятельства укладывания; личные заметки,
  дата рождения, сведения о здоровье, email и пароль не публикуются. Блокировка владельца
  также закрывает доступ. Публичный отчёт не даёт права редактировать дневник.

CSV собирается на клиенте из ответа отчёта: UTF-8 с BOM, разделитель `;`, факты сна,
без прогнозов. У открытого сна нет окончания и длительности. Личные заметки включаются
только по отдельному выбору владельца; публичный экспорт их не содержит. Значения,
которые могут быть формулами таблицы, экранируются.
